# 可用性审计（用户视角）

> **问题不是"能不能算"，而是"用户会怎么做、那条路通不通"。**
> 这份审计换了提问方式：对每一件用户想做的事，先问**他最可能的动作是什么**（打字？点球？拖？），
> 再实测那条路。与 [TASKS.md](TASKS.md) 互补——那份是"输入视角"（这行定义能不能算），
> 这份是"**动作视角**"（用户想到这件事时，手往哪儿放）。
>
> 数据来源（都是实测，不是推理）：
> - **可点性地图**：`opsFor` / `singleOpsFor` / `multiOps` 是纯函数，直接枚举每种"选中"给出的候选
> - **任务重跑**：`docs/TASKS.md` 那份清单按输入逐条重跑（原脚本在已删的 `.tmp-verify/` 里，本次重写）
> - **真浏览器走查**：`apps/web/verify/e2e/`（交互层）
>
> 探针在 `apps/web/.tmp-probe/`（临时目录，结论在这里）。

## 0. 一句话结论

**数学能力已经不缺（2026-09-25 审计时：55 条里 45 条能算），缺的是"路"。**

审计当时有三个操作入口（左栏表 / 对象悬浮球 / 多对象球 ⊕）**本质是同一个模式的三种外壳**：
**先选操作，再点参数**。而用户脑子里先有的是**"把这两个凑一起"**——这条方向的路没有。
于是凡是要"关联两样东西"的意图（`f(H)`、`H ⊆ G`、`K ⊴ S₄`），一律只能打字；打不出来就卡死。

> **后续**：第四条路已经补上（U21 拖拽连线：拖 A 到 B 松手 → "这两个能做的事"），
> §2.2 / §2.3 / §3.C 的那些 ❌ 逐条修完（U19–U21）；U27 又把 core 里"能算但没接"的一批接上了。

## 1. 三条路径的现状

| 路径 | 用户怎么做 | 现状 | 代价 |
|---|---|---|---|
| **打字** | 点 `✎` → 手写 `K = ker(f)` | 最可靠，覆盖注册表全部 38 条操作 | 要记住操作名（U25 起输入只认 ASCII，`\varphi` 这类写法面板上随处可抄） |
| **选操作 → 点参数** | 球 / ⊕球 → 选操作 → 点对象 | 通（`opsFor` 保证候选与可点一致） | **方向反了**；且"不上画布的对象"选不到 —— 后者已由**对象列表行上的「操作」**补上（U21 加在信息面板、**U44 挪到行上**） |
| **直接操作对象** | 拖 A 到 B、拉连线 | ✅ **U21 落地**（唯一候选直接执行，多个弹菜单） | —— |

**这是本审计最实的一条发现**（也是 U21 的全部动机）：不是操作不够，是**中间产物没有操作入口**。

## 4. 输入契约的破口

| 现象 | 实测 | 性质 |
|---|---|---|
| **φ 敲不出来** | `checkName('\phi')` → `ok:false`（"名字只能用字母（含希腊字母）/ 数字 / 下划线 / 中文"）；字符 `φ` 本身合法 | 系统在模板里写 `φ = 映射(...)`，用户却敲不出——**违反"展示成什么样就得能照着敲回去"这条契约** |
| 操作名当群记号解析 | 打 `极大子群(G)` → 报"无法识别：极大子群(G)｜无法识别的群记号 …可用写法：C₁₂ · S₃ · D₄ ……" | **完全误导**：用户会以为要输群记号 |
| 关系写成 `⊆` | 打 `H ⊆ G` → 报"缺少「=」" | 用户写的是关系，系统当成漏了等号 |
| 未支持 vs 打错字 | `Burnside(A)` / `gcd(12,18)` / `φ(12)` 与"手滑打错"给**同一句**报错 | 用户分不清"没这个功能"还是"我打错了" |

> **四条都已修**（U18 修报错文案，U25 定下"输入只认 ASCII"的形态；U27 把 `gcd` / `Burnside(A)` 变成真操作）。
> 保留在这里是因为它们是"输入契约"这一层的**原始病历**：以后出现"用户敲不出来 / 报错答非所问"，
> 先回来看这四条的形状。

## 5. 结论区的沉默规律（"K 是什么"的根因）

实测 `groupInsights` 对几个典型对象：

| 对象 | 符号 | 识别结果 | 结论条数 |
|---|---|---|---|
| `G = S_4` | `S_{4}` | `S_{4}` | 1（只有"阶"） |
| `Q = 商(G, N)` | `S_{4}/N` | `S_{3}` | **2（同构 + 阶）** ✅ |
| `K = ker(f)` | `C_{2}` | `C_{2}` | 1（只有"阶"） |
| `H = 闭包(G, r)` | `C_{4}` | `C_{4}` | 1（只有"阶"） |

**规律**：判据是"识别结果 ≠ 自身符号才说"。
- 商的符号是**构造记号**（`S₄/N`）→ 与识别结果不同 → **说话** ✅
- 核 / 像 / 子群的符号是**结构记号**（`C₂`、`C₂×C₂`）→ 与识别结果相同 → **永远沉默** ❌

而**结构记号恰恰是构造物的常态**。于是"K 是什么"这个问题，在系统里**没有地方回答**。
另外"基本"tab 的「识别」行依赖 `group.isoSymbol` —— 那是**只有从小群库建出来的群**才有的字段，
`createGroupFromSymbol` / `buildSubgroupGroup` 都没有 → **那行基本是死代码**。

> **U18 已修**（见 §6.1）：判据改成看 `node.opId` —— 由操作构造的一律说，并给 SmallGroup 编号与惯用名；
> 那行死代码删了。这一节保留为"当初为什么会沉默"的**根因记录**（U19 的关系层也沿用了同一条"看它怎么来的"判据）。

### 6.2 U19 做了什么（2026-09-25）—— 关系层

**新增 `gal/relations.ts`。** 关系的来源**只有两条，都不猜**：

| 来源 | 覆盖什么 | 例（实测） |
|---|---|---|
| **① 由来源决定**（`node.sources` + `node.opId`） | `ker` / `im` / `Z(G)` / `C_G(S)` / `N_G(H)` / `[G,G]` / `⟨S⟩` / `A∩B` / `商` | `K = ker f ⊴ S₄ · 指数 [S₄:K] = 24 / 4 = 6` |
| **② 元素集包含**（`containment()`，三道关） | **两个各自独立声明的群之间** | 手打 `A_4` 与 `S_4` → `A₄ ≤ S₄` · ⊴ 正规 · 指数 24 / 12 = 2 |

包含判定的**三道关**（`containment()`）：

1. `H` 的每个元素 id 都能在 `G` 里找到（id 空间一致）
2. `subgroupFromElementIds(G, ids)` 认可（含单位元 + 乘法封闭）
3. 校验出的子群阶 **= `|H|`**

再拿 `findAllNormalSubgroups(G)` 判 ⊴（按 `subgroupSetKey` 比对，超枚举守卫则不判定）。

**为什么必须这么严**（实测，两条都是假阳性陷阱）：

| 陷阱 | 现象 | 挡住它的是 |
|---|---|---|
| `V₄` vs `D₄` | `subgroupFromElementIds(D_4, ['e','a','b','c'])` **不报错** —— 它把认不得的引用一丢了之，返回**平凡子群** → 朴素写法得出 `V₄ ≤ D₄` | 第 ① ③ 关（V₄ 的 id 是 `e a b c`，D₄ 的是 `r0…s3`，一个都找不到） |
| `C₂` vs `C₄` | id 是**真前缀关系**（`e0 e1` ⊂ `e0 e1 e2 e3`），第 ① 关**会通过** | 第 ② 关（`e1 + e1 = e2 ∉ {e0,e1}`，乘法不封闭） |

**三条纪律：**

- **指数 1 单列成「同一」** —— `[G:K] = 1` ⟺ 元素完全相同 ⟺ 同一个群。
  `ker f` 与 `闭包(G, (12)(34), (13)(24))` 都是 V₄、元素 id 一模一样；
  两个各自声明的 `C_6` 也一样（同一批 `e0…e5`）。写成一对"互为指数 1 的子群"会被读成两个东西。
- **假阳性必须为 0** —— 上面那张表的两条都写成了断言。
- **边界写在面板上** —— 那一节只列「已经建出来」的对象之间的关系，末尾一行明说；
  免得被读成"全部关系"（与 U18 给子群 tab 加"共轭类代表"是同一个教训）。

**面板落点**：信息面板在**结论层与 tab 之间**插一节「关系」。每行 = 类标签（核 / 像 / 商 / 同一 / 子群 / 包含 / 派生）
+ 关系式（KaTeX）+ 附注（记号对照 · ⊴ 正规 / 非正规 · 指数手算式）。每类有上限，截掉的只说个数。
反向给「派生」：**点画布上的箭头 `f`**，就能看到它长出了 `K = ker f`。

**与"拉箭头"的边界**：这一批是**把关系说清楚**（文字 + 手算数字，可点、可核）。
画布上真的长出那根箭头，是下一批（`包含(H, G)` 操作 + `relation` 值类型）。

### 6.3 U20 做了什么（2026-09-25）—— 子群像 + 声明包含

用户原始投诉的 ③④ 两条，都是"想做但没这个功能"。**走的是 (a)：做成操作**（而不是纯手势）。

| 操作 | 怎么写 | 关键设计 |
|---|---|---|
| **子群像** | `像(f, H)`（`H ≤ 定义域`） | 与 `像(f)`（整个像）**同一个 op** 的可选第二参——用户嘴里都叫"像"，别名只该指向一条路 |
| **声明包含** | `R = A ⊆ B` / `A⊆B` / `包含(A, B)` | **新值类型 `relation`**，`sortOf → edge`（是边不是顶点）→ 自动获得三个入口、可点选、可删、可进证明模板 |

**判据同源**：`包含(H, G)` 用的是 U19 那份 `containment()`（三道关）。于是"声明出来的关系"与信息面板里"算出来的关系"**永远一致**，不会出现两种说法。

**正规性不是声明的，是算出来的**：用户只说 `⊆`；`⊴` 由工具现场判。所以没有"声明正规子群"这个操作，也无从撒谎。非正规的 `↪`、正规的 `⊴`，画布上一眼可分。

**拦得住假声明**（每一条都给了理由，且都是**输入层**就拦）：

| 写法 | 报什么 |
|---|---|
| `D ⊆ G`（D₄ vs S₄） | 「D」不是「G」的子群 · 元素不是子集，或对乘法不封闭 |
| `X ⊆ Y`（C₂ vs C₄，id 是真前缀） | 同上（挡住它的是乘法封闭） |
| `X ⊆ Y`（C₄ ⊆ C₂，阶反了） | \|X\| = 4 > \|Y\| = 2，不可能是它的子群 |
| `X ⊆ Y`（两个 C₆，元素完全相同） | 元素完全相同，就是同一个群（包含是严格小于） |
| `A ⊆ K9`（K9 打错） | 「K9」算不出来：无法识别：K9 ← 这条**不再**答非所问地说"这行写的是一个关系" |

**顺带修掉一个布局老 bug**（U20 之前就有，只是新功能让它变得容易撞上）：
两条水平边**共用一个端点**时（`A ⊆ G` 与 `G → f → S₃`），老的列序规则"把夹在中间的组挪到行尾"会自相打架 ——
满足一条就把另一条弄坏。实测 `psi: B→G` 从 `H` 身上横穿过去，违反 DIAGRAM_SPEC §1.2。
新规则：把水平边当约束图，**分量内穷举列序，取"被夹住的边最少"的那个**；并列只接受严格更优（布局要稳）。
`H·G·B` 于是排成一条链。

### 6.5 U21 做了什么（2026-09-26）—— 拖拽连线 + 面板「可做」

### 6.8 U26 做了什么（2026-09-28）—— 结构伴生边的语义身份

缺口清单里最后一条"用户会撞上"的：画布上的 `π` / `π₁` / `↪` / `=` / `≅` 是
**操作的结构顺手长出来的箭头**（`alongsideEdges` + 轨道边），背后没有对象，
U3.1 的 `objectId` 那条路对它们根本不适用 —— 于是它们成了画布上唯一点不动的东西。
**默认示范页面上就有两条**（`O = Ω` 与 `N ↪ G`），一进页面就撞。

**为什么不是"升级成一等对象"**：一等对象意味着进对象表、能被引用、挂悬浮球、
列 `ker` / `im` —— 可伴生边不在对象表里，列出来的按钮**点了必然报错**。
所以走第三条路：给它一份**语义身份**（`StructuralEdge`：kind + 两端 + 一句话 +
就地算好的账），焦点走独立前缀 `struct:<边 id>`，信息面板单开一节「这条箭头」。

| 点开的边 | 面板说什么（全部手算核对） |
|---|---|
| `π : G ↠ G/N` | 自然投影（商映射）· 核 = N · \|Q\| = \|G\| / \|N\| · 满射 |
| `π₁ : A×B ↠ A` | 积投影 · 核 = 另一个因子 · 满射 |
| `H ↪ G`（含 `⊴`） | 包含 · 指数 [G:H] · 正规 / 非正规（走 `containment()`） |
| `Orb = Ω` | 相等 · \|Orb\| = \|Ω\| · **传递** |
| `G/ker φ ≅ im φ` | 同构 · 两边同阶 |

三条纪律（都写成了断言，见 `suites/structural.ts` 31 条 + `e2e/structural-edges.mjs` 34 条）：

1. **菜单不撒谎** —— 不是对象 → **不挂悬浮球**（走查钉住"点伴生边后球数为 0"）。
2. **判据同源** —— 指数与正规性与信息面板"关系"节用同一份 `containment()`；
   核与阶读操作已知的输入。
3. **视觉身份不变** —— 可点了，但**仍是蓝灰细线**：可点改的是"能不能被问账"，
   不是它在图里的分量。

**顺手修掉一个展示老毛病**：包含边的标签从前硬写 `\hookrightarrow`，于是
`Z(G) ⊴ G`、`ker f ⊴ dom`、`C₃ ⊴ S₃`、`im φ ⊴ C₆`（**交换群**的子群全正规）
这些定理级的正规包含全被画成普通单射，与面板说的"⊴ 正规"自相矛盾。
现在标签也由 `containment` 定。受影响的是**期望值**，逐条手算核对后更新。

**这一批逼出来一个潜伏真 bug**（值得单独立此存照）：`containment` 的缓存 key
只看 `symbol#order` —— 记号与阶相同的两个群（从记号建的 `C₂` vs 从 `C₄` 里摘
出来的 2 阶子群）会**串**。从前它只在用户点开面板时被调用，撞上的概率低；
这一轮让**画布派生**也要问包含关系，调用面一宽就露了。修法：key 加**元素 id
指纹**（且连着记号 —— `V₄` 与 `C₄` 的元素 id 恰好都是 `e0..e3`）。



### 6.9 U27 做了什么（2026-09-28）—— core 接线：判定与结构

### 6.22 第十八批做了什么（2026-09-30）—— 独立构造的群之间的**包含**

**用户原话**：

> 「怎么又是 V4 的问题，A4 能拉包含箭头到 S4 上，V4 却做不到，到底再弄些什么……
> C3 也拉不了包含箭头到 S4/V4，能不能把 V4 修完？这么简单的问题你哪怕硬编码都早解决了吧？」

**根因**（不是"V4 特殊"，是判据的适用范围）：`relations.containment` 从前**只认"元素 id 逐个对得上"**。
`S_4` / `A_4` 的元素 id 是**置换本身**（`1,2,3,4` —— 自证式，跨群可比），所以 A₄ ⊆ S₄ 一判就中；
而 `V_4` 的元素是抽象记号 `e a b c`、`C_3` 是 `e0 e1 e2`（**群内编号**，跨群会撞号）——
与 S₄ 的置换根本对不上，于是被判"不是子群"。**A₄ 能用只是因为它恰好是置换群**。

这正是 §3.1 里记的那条"等用户点名的设计岔路"：`包含` / `像` 遇独立构造的群要不要自动翻译。
用户点名了，所以这一批把它补上。

**㉖ 第二关：嵌入**（`relations.ts#embeddingContainment`）。

`containment` 现在是**两关**：

| 关 | 判据 | 成本 | 语义 |
|---|---|---|---|
| ① 字面包含 | 元素 id 空间对得上 + core 的 `subgroupFromElementIds` 认可（含单位元 + 乘闭）+ 阶相等 | 便宜 | "同一个世界里的**真子集**"（U19 起就有） |
| ② 嵌入 | **G 里有没有与 H 同构的子群**（按阶 + `subgroupStructureSymbol` 筛 `findAllSubgroups(G)`） | 见下 | "H **同构于** G 的某个子群" |

第二关不是特例化，是数学：`H ≤ G` ⟺ `G` 有一个子群 ≅ `H`。所以 `V₄ ≤ S₄`（S₄ 有 4 个 Klein）、
`C₃ ≤ S₄`（4 个 Sylow 3-子群）、`D₄ ≤ S₄`（3 个 Sylow 2-子群）、`C₂ ≤ C₄` 全都**真的成立** ——
从前一律被拦。

**三条边界**（每条都有理由，不是随手加的）：

- **只认严格包含**（`|H| < |G|`）。两个各自造的同阶群互为同构，但它们是**两个对象**；
  说"同一个群"是假话 —— 那是指数 1 档（第一关）的语义，不能借第二关混进来。
- **正规性说不准就说"未判定"**：H 是个**裸群对象**，没指定嵌进 G 的哪个子群。
  候选唯一 → 用它的；候选多个但态度一致 → 照实说；**态度不一致**（`V₄` 在 `S₄` 里正是这种：
  4 个 Klein 只有 1 个正规）→ `normal = null`，画 `↪` 不画 `⊴`。**`⊴` 是有断言力的符号**。
- **商群不参与**：任一边带陪集元素（`qcoset-i`）就停 —— 跨"层级"的包含不做嵌入判定
  （与 U30 的 `autoTranslatedSubgroup` 同款边界）。

**㉗ 成本与"未判定"**。这条搜索进了**拖拽路径**（`pairOps` → `containment`），而实测开销差得很远：

| G | 阶 | 子群数 | `findAllSubgroups` |
|---|---|---|---|
| `S_4` | 24 | 29 | **3 ms** |
| `A_5` | 60 | 58 | 57 ms |
| `C_2^4` | 16 | 66 | 7 ms |
| `C_2^5` | 32 | 373 | 437 ms |
| `S_5` | **120** | 155 | **1.25 s** |

（`|G|` 不是好的开销预测 —— 32 阶的初等阿贝尔群比 60 阶的 A₅ 贵 8 倍。）
所以：
- 枚举上限用项目既有的 `ENUM_LIMIT = 120`（core 的"2 秒线"是 144）；`findAllSubgroups` 的结果
  **按群对象 `WeakMap` 记忆**（同一个群问第二次免费）；
- 超限 / 带陪集 ⇒ **不搜**，并且新增 `embeddingSearchBlocked()` 让报错语改口说
  **"没能判定"**而不是"不是子群"—— 后者是**假话**。这是"算不动就说算不动"的老规矩，
  和 `normal: null` 的"未判定"同源。

**㉘ 三种"没有"分得开**（`包含` 操作的报错语，按从硬到软排）：

| 情形 | 一句话 | 凭什么 |
|---|---|---|
| 阶不整除 | `|C_3| = 3 不整除 |V_4| = 4，按拉格朗日定理不可能是子群` | **证明**了没有（新增的先行检查） |
| 阶整除、搜过确实没有 | `S_4 里没有与 Q_8 同构的子群（已枚举全部子群）` | **算出来的**结论（"不是子群"这句现在有底气） |
| 群太大 / 带陪集 | `没能判定「…」是不是「…」的子群` + `没做嵌入枚举` | **没算**（不许冒充结论） |

第三种是这一批**新造的必要区分**：从前的 `null` 只有一个意思（"不是"），现在必须分清
"不是"与"不知道"。**唯一的例外是 `像(f, H)`** —— 它仍然只认"元素取自定义域"：
`f(H)` 是个**具体的子群**，而 H 有多个嵌入时"取哪个的像"说不准（不同的嵌入可以给出不同构的像）。
关系是 yes/no，像是一个具体的群 —— 这两件事不能一起放宽。

### 6.23 第十九批做了什么（2026-09-30）—— 陪集层判定（对应定理）+ 一处守卫 + 两处渲染

用户四条追问（附图），逐条查证。

#### ㉚ "怎么判子群/正规子群？能不能跳过元素直接判？"

**能"跳过元素"的部分已经在做** —— `containment` 的**第二关**就是"在 G 里找与 H 同构的子群"
（纯结构问题，不比 id）。**但正规性跳不过去**：`H ≤ G` 问"G 里有没有 H 的拷贝"；
`H ⊴ G` 问"**那个具体的拷贝**稳不稳"—— 得先知道是**哪一个**。`S₄` 有 4 个 Klein 子群、
只有 1 个正规；用户给的是裸群 `V_4`，"是哪一个"无解 ⇒ `normal: null`（未判定）
是**数学上的诚实**，不是偷懒、也不是没算。

#### ㉛ "C₃ 不是 S₄/V₄ 的子群？S₄/V₄ 不是和 S₃ 同构？这都判断不了还做不做群论计算器？"

**用户对，是守卫写错了**（U38 留下的）。探针实测：

| 检查 | 结果 |
|---|---|
| `subgroupStructureSymbol(S_4/V_4)` | `D_{3}` —— **算得出** |
| `findAllSubgroups(S_4/V_4)` | 5 个（阶 1,2,3）—— **跑得动** |
| `isomorphicSubgroupsIn(S_4/V_4, C_3)` | **1** —— 真找到了那个 C₃ |
| `containment(C_3, S_4/V_4)` | **null** ← 被 `hasCosetElements(G)` 挡死 |

守卫从前是"**任一边**带陪集就跳过"—— 过宽（把"G 是商群"也一刀切），报错语还谎称"阶 6 太大"
（阶 6 跟"大"毫无关系）。**收窄成"只挡 H 是陪集层对象"**（那才真跨层级）后：
`C_3 ⊴ S_4/V_4`，指数 2（手算 `|S_4/V_4| = 6`，`6/3 = 2`；`S_3` 的 3 阶子群唯一 ⇒ 正规）。
**用户给的对应定理（第四同构定理）**正是这件事的保证：`N ⊴ G` ⇒
`{H : N ≤ H ≤ G} ↔ {S : S ≤ G/N}` 保包含双射（正规性一一对应）——
"商群的子群"是有定理撑腰的判定对象，不是禁区。

#### ㉜ 子群列表：`trianglelefteq` 与"重复"

- **`trianglelefteq` 是渲染 bug**：那处写成了 JSX 属性**字面量** `<Tex tex="\\trianglelefteq" />`，
  而**属性字面量里的反斜杠不转义** ⇒ KaTeX 收到 `\\`（换行）+ 文本，界面就真的显示 `trianglelefteq`。
  （改成表达式 `{'\trianglelefteq'}` 也**不对** —— `\t` 变制表符，**首字母消失**。
  正解 `{'\\trianglelefteq'}`。坑记 `verify/README.md` 44。）
- **`「\xn」` 是笔误**（想写 `-xN`），而且那段是**纯文本面**却写了 LaTeX ——
  顺带去掉 `**粗体**` 星号（纯文本面不认 markdown）。
- **同类第三处**：`SubgroupTag` 里 `{"\\normal in"}` 同样把 LaTeX 原样漏在界面上
  （`Sub(G)` / `正规子群(G)` 的标签会显示 `\normal in`）—— 一并改成 `{'\\trianglelefteq'}`。
- **"重复"本身没动**：那 9 行是 S₄ 的 **9 个共轭类**（数学上正确的划分）。`C₂` 两行 =
  换位类(×6) vs 双对换类(×3)；`C₂×C₂` 两行 = 非正规类(×3) vs 正规 V₄(×1) ——
  **同构但不共轭**。只列符号就看着像重复。**要不要改成"按同构类合并"**（`C₂ x9` 一行、
  展开看共轭类）**等用户拍板** —— 那会牺牲"正规性差异"的一眼可见性。

#### ㉝ "常见群有没有打表？"

### 6.24 第二十批做了什么（U40，2026-09-30）—— 把对应定理**真做进项目**

**用户原话**：

上一轮我交的是一张**设计稿**（`show_widget` 画的两栏格示意）—— 用户不接受，接着又指出
更根本的一层：**一个群论计算器要展示对应定理，就得在它自己里展示**；另手写一个 HTML 页面
出来，恰恰证明了这件事没做进项目。

这一批把它做进去，路径是：`信息面板 → 子群 tab → 正规那一行右边的「对应」`。

#### 定理与两个关键判据

`N ⊴ G ⇒ { H : N ≤ H ≤ G } ⟷ { S : S ≤ G/N }`，`H ↦ H/N`，保包含、保正规。

1. **`H ↦ H/N` 按陪集成员真配对，不按阶配**。`computeQuotientGroup` 给的商群元素带
   `cosetMemberLabels`（这个陪集里有哪些元素），拿 `H` 里元素的 label 去查它落在哪个陪集，
   落在同一个陪集的合成一个像点。**按阶配在多解时会排错**（S₄ 里三个 D₄ 同阶、三个 C₂ 同阶），
   按 label 配天然正确 —— 而且"每个 H 恰好落到一个子群上、没有两个落同一个"这件事本身
   **就是双射的证明**。
2. **不用 `getPrecomputed`**（第十九批查过的那张预计算表）：它只覆盖库内具名群，
   而这里的主角常常是构造物（`S_4/V_4`）—— 实测返回 `null`。

#### 三条边界（都真踩到）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| ① | 卡片报"要求 N ⊴ G"，可 A₄ 明明是 S₄ 的正规子群 | `subgroupFromElementIds` 造出的 `Subgroup` 只保证"是子群"，**`isNormal` 一律 `false`** | 正规性读**子群格节点**（`computeSubgroupLattice` 的 `isNormal` 是真算过的） |
| ② | 过了 ① 仍报"算不出商群" | core 的 `computeQuotientGroup` **自己会读 `normalSubgroup.isNormal`**，读到 `false` 直接 `null` | 用 `findAllSubgroups(G)` 里那个**真**子群对象（`gal/correspondence.ts#findSubgroup`） |
| ③ | 走查"点到了 Klein 那一行"误报 FAIL | KaTeX 渲染后的 `textContent` 带**零宽字符**（`C2×C2` 直接 `===` 比不等） | 走查里先清洗 `[\u200b-\u200d\ufeff]` 再比 |

**坑 ①② 是同一件事的两面**：core 有两套"取子群"的入口 —— `subgroupFromElementIds` 是
**轻量的**（只查"含单位元 + 乘封闭"），`findAllSubgroups` 是**全量的**（顺带算正规性、指数、
生成元）。凡下游要读 `isNormal`，**必须用后者**。

#### 摆位（为什么同层一定对得上）

两侧各自按阶降序分层。因为 `|H/N| = |H| / |N|`，**降序是同序的** ⇒ 左右同层；层内再按配对
给同一 `slot` ⇒ 左右逐列对齐。编号 ①..⑥ 把"哪一对"直接标在图上。

| 层数 | 4（24 / 12 / 8 / 4 ↔ 6 / 3 / 2 / 1） |

1. 左上已经三个抽屉（对象 / 操作 / 信息），右上还有证明面板 —— 窄屏（≤1080px）下
   现有两块都要各占一半才不打架（U41 刚修的那条），再加一块只会更挤；
2. tab 是**同一个对象的三种看法**（基本 / 元素 / 子群）。拆成两块面板就变成
   "看元素要往另一个地方看"，和"用户应该在对象旁边完成他想要的操作"正相反；
3. 分区的成本是一个 CSS 类，新开面板要动布局、拖拽、收起状态、窄屏规则。

代价是元素 tab 底下留一段空白（表 127 + 头 29 = 156，tab 区 279）。
这段空白换来的是**位置稳定** —— 不选"高度随内容"正因为：子群 tab 的列表是 486px，
元素 tab 只有 156px，高度随内容就意味着每切一次 tab 整条 tab 栏上下跳一次。

对照理念「画布是操作台，**用户在对象旁边完成它的操作**」：把对应定理做成
"点一行 → 看一张图"，方向本身就错。⇒ 整条链路删除（UI + 算法 + 两套回归 + CSS + 文档清单）；
**陪集层的判定留着**（U38/U39 的 `C_3 ⊴ S_4/V_4` 是**计算**，不是展示）。

#### ② 元素表折叠：治错了病

U41 第 ③ 条的诊断链是：

| 现象 | U41 当时的判断 | 实际 |
|---|---|---|
| 元素表右边两列看不到 | 行太多（24 行）⇒ 按共轭类折成 5 行 | **宽度**病：6 列塞进 298px，表宽 335 > 282，右两列被裁 |

折叠治的是**行数**，病在**宽度** —— 治错了地方，还多付一个代价：把**单个元素**藏进展开态，
而用户恰恰要看的就是它。这和 U42 的发现合起来是一件事的两面（U42 说"真正的病是够不着
可视高度，不是表太宽"）：**盯住"用户看不到什么"，别盯"我该怎么化简"。**

做法：行 = 元素照旧（24 行），列 = 元素 / 阶 / `\in Z?` / 共轭类 / 类大小 / 中心化子；
宽度靠**列头收短 + 横向 padding 6 → 4px** 兜住（实测原来越出 4px，收完 0）。

顺带修掉一条被压扁的坑：`.info-panel-body` 是 flex column，`.etable-wrap` 默认
`flex-shrink: 1` ⇒ 24 行的表被压扁到容器高，滚动落到**表自己**身上（`info-panel-body`
反而没得滚）。加 `flex: none`，让表吃满内容高、由 tab 区滚。

| A₅ | 60 | 61ms |
| **C₂⁵** | **32** | **472ms** |
| S₅ | 120 | 2.1s |

1. **`SUB_COUNT_CAP = 60`**（与 `gal/structure.ts` 的 `STRUCTURE_CAP` 同源）—— 超限**不报数字**，
   标题行只留标签（**宁可没有数字，也不写个猜的**）；
2. **计算放到当前任务之后**（`setTimeout` 0）—— 面板先画出来再枚举，点一个群不该为了一个折叠标题卡住；
3. 结果进 **`WeakMap`**（按对象身份，同 `gal/identity.ts` 的纪律），同一个群反复聚焦只算一次。

**口径对齐**：标题里的表达式与 `SubgroupsTab` 的 `structKey` **同一个**（`s.structure ?? \`阶 ${s.order}\``），
标题与正文的数字不许打架。

### 6.31 第二十七批做了什么（U47，2026-10-01）—— 本地预算：`Aut(S_6)` 把页面卡死

> 「我输入Aut(S6)，敲完6，网站直接卡死了。处理一下」

#### 为什么"算不完"在这里 = "死机"

输入球的预览是**每次输入同步求值**（`ComposerOrb` 的 `useMemo` → `evalExpr`）。
一条要跑 240s 的操作，在这条路上不是"慢"，是**整个页面不动**（连光标都不闪、
连"正在算"都显示不出来）。所以判据不能是"算完再判超时"——只能**在调用前**挡住。

把 S₆ 上全部重操作扫了一遍，空白是三处（不是一处）：

| 位置 | 症状 | 根因 |
|---|---|---|
| `Aut(G)` | **240s 没完** | core 的守卫只看**候选组合数**（`AUTOMORPHISM_MAX_COMBINATIONS = 30000`），S₆ 的 **18000 组正好从它下面钻过去** |
| `Syl_p` / `pSub` | **45s 没完** | core 内部**没有**守卫（`SYLOW_MAX_ORDER = 144` 只用在 Sylow **分析**上，没用在**枚举**上） |
| `Sub` / `正规子群` | **"0 个子群"**（不卡，但答案是假的） | core 超限 `if (order > 144) return []`，调用方照单全收就是"S₆ 有 0 个子群" |

#### `Aut`：两段代价差着数量级（新 `gal/automorphisms.ts`）

`createAutomorphismGroup` 其实是两件事，实测（node 22，本机）：

|---|---|---|---|---|---|
| C₆ | 6 | 2 | 2 | 8ms | 1ms |
| Q₈ | 8 | 36 | 24 | 9ms | 20ms |

| C₃×C₃ | 9 | 4 | 48 | 11ms | 181ms |

| A₅ | 60 | 360 | 120 | 280ms | **21s** |
| **C₂³** | **8** | 343 | **168** | 26ms | **60s 都没完** |
| S₅ | 120 | 600 | 120 | 1.9s | 40s 都没完 |
| C₃³ | 27 | 17576 | 11232 | 9.6s | — |
| **S₆** | **720** | **18000** | 1440（课本值，本地搜不出来） | **240s 都没完** | — |

两条判据：

1. **自变量是 `|Aut|` 不是 `|G|`** —— `C₂³` 只有 8 阶，`|Aut| = |GL(3,2)| = 168`，照样死机。

2. **搜索 ≈ 组合数 × 阶 × 0.02ms**（6 个点拟合，误差 2 倍内）。组合数的算法与 core

⇒ 两段守卫：**搜索线 `组合数 × 阶 ≤ 30000`**、**建群线 `|Aut| ≤ 48`**（线取实测还跑得动的
一侧：搜索放行到 600ms，建群放行到 200ms）。第二段报错**带上已经算出来的 `|Aut|`** ——
`Aut(A₅)` 会说"有 **120** 个自同构，本地建不出这个群"，那是真答案。

#### `Syl_p` / `pSub`：判据不是阶，是 **p-元素密度**

core 的 144 线对这条枚举**不管用**：**64 阶的 `C₂⁶` 在 144 之下照样 60s 没完**。
真正的自变量是 **p-子群个数**（core 的 `vi()` 对每个 p-元素、与每个已找到的子群
合并一次闭包，闭包又是 O(子群²)）—— 而那正是要算的东西，不能拿来当判据。
改用"**p-元素对数 ÷ 阶**"当代理：

### 6.33 第二十九批做了什么（U49，2026-10-01）—— 本地补的记号：`S6` 能算，`A6` 也得能算

#### 用户报的原话

U48 把 `A_n`（n ≥ 6）"本地建不出来"当成一条**边界**写进了回归（§6.32 第 4 条）。用户当场不接受：

> 「逗我吗，S6能算，A6不能算？」

#### 查下去：不是"算不动"，是 core 的一处自相矛盾

| 位置 | 写的是什么 | 结果 |
|---|---|---|
| `groupFactory.ts` 的 `S_{n}` 门 | `2 ≤ n ≤ 6` | `S_6` ✅（`createSymmetricGroup` **没有任何内部上限**）|
| `groupFactory.ts` 的 `A_{n}` 门 | `3 ≤ n ≤ 6` | 门的**本意就是支持到 `A_6`** |
| `AlternatingGroup.ts` 的构造器 | `if (n > 5) throw 'A_{n} for n > 5 is too large'` | **`A_6` 过了门、死在构造器** ❌ |

⇒ 720 元的 `S_6` 建得，360 元的 `A_6` 建不得。同类的还有 `D_16`（32 阶被挡，而 `C_2^5` 32 阶能建）、
`GL(2,4)`（180 阶被挡）—— 用户拍板**这一批只补 `A_n` 这一处**。

#### 用户拍板的两件事

- **修在哪**：**应用层**。Galculator 吃的是 npm 上的 `@groupviz/core`（锁 2.3.0；npm latest 2.4.0 也带着
  同一个 bug），动 core 要改 GroupViz + 发版 + 升级 + 联网装包 —— 这笔账记在下面。
- **放多宽**：只修 `A_n` 这处（`A_7` 仍建不出，因为它得从 `S_7` 拿，而 `S_7` 本身也超门）。

> ⚠️ **U50 更正（见 §6.34）**：后半句当时是**对 core 的转述**、现在不成立了 —— `S_7` 的门是被写窄的
> （`createSymmetricGroup` 没有内部上限，实测 5040 元 8ms），U50 把 `S_n` 补到 `n ≤ 7`，
> `A_7` 因此跟着能建（2520 元）。**"core 建不出"要分成"真算不动"和"门写窄了"两类**，
> 这一条当时归错了类。

#### 做了什么

新增 `gal/localBuild.ts`。核心观察：**`A_n` 就是 `S_n` 的偶置换子群**，而 core 自带
`buildSubgroupGroup(parent, elements, symbol, generators?)` —— 把"父群里的一堆元素"包成一个群，
`multiply`/`inverse` 直接继承父群（元素 id 因此与父群一致）。**一行置换数学都不用抄。**

三条纪律：

1. **借哪个父群就受哪个父群的门限**（`S_n` 的门 = 6）—— 不是"放开到随便多少阶"；
2. **core 建得出的不许抢**：`A_3`/`A_4`/`A_5` 一律返回 `null`，否则同一个记号会长出两个
   互相独立、只是**同构**的群对象。这条**由函数自己守**（函数内再 `parseGroupNotation` 探一次），
   不指望调用方记得；
3. **不猜**：拿不到父群 / 偶置换不是恰好一半 / 闭包尺寸对不上 —— 一律 `null`，调用方照原样报错。

#### 唯一的真技术判断：生成元必须自校验

`buildSubgroupGroup` **不检查**传进去的生成元是否真能生成那堆元素。而 `minimalGenerators`
在 360 元上要 **4.2 秒**（实测，太慢，不能留给它去挑）。

于是给候选对 `(1 2 3)` 与 `(2 3 ... n)`，**先算闭包验尺寸 + 验全偶**；不过就退到
"全部 3-循环 `(1 2 i)`"（A_n 由 3-循环生成，是定理）。

**为什么这条不能省**：实测 `(123),(12345)` 的闭包**只有 60 阶**，`(123),(23456)` 才是 360。
`buildSubgroupGroup` 照单全收 —— 挑错的后果不是崩，是面板上给出
"**生成元生成不出这个群**"的假象。那比报错更难查。

#### 接线四处

| 位置 | 为什么 |
|---|---|
| `evalDef`（`!n.symbol` 分支）| 打 `A_6` 要变成一个真群，不能再报"该记号本地建不了 / 需要后端 GAP" |
| `proof.stageInfo` + `groupOf` | 体检与建群用**同一份判据**，面板说"能用"就得真能跑（阶上限那关照旧拦得住 360）|
| `known.realizeKnownGroup` | `build: 'A_{6}'` 这才真落得下来 —— `[S_6, S_6] = A_6` 从「已知群」变成**真群** |

#### 效果（真跑）

- 打 `A_6` **当场**变成一个真群：`order = 360`、`elements.length = 360`、**不是**「已知群」；
  实测元素阶分布 `1^1 2^45 3^80 4^90 5^144`，与 A_6 的真分布一致
  （80 = 3-循环 40 + 两个不交 3-循环 40；90 = 4-轮换乘对换）—— 这条是**强不变量**，
  能抓住"建出来的其实是别的 360 阶群"；

### 6.34 第三十批做了什么（U50，2026-10-02）—— 常见族本地收口：`Aut` 建群线 + `GL/SL/PGL/PSL` + 门窄的 `S_n/D_n/C_n`

#### 用户报的原话（两张截图 + 一句反问）

截图一：`AUT(C4^2)` → 「C_4^2 有 **96** 个自同构，**本地建不出这个群**，建群线 48，**待后端 GAP 通道**」
截图二：`GL(2,4)` → 「**该记号本地建不了**……（**后端通道尚未接入**）」

#### 分诊：这两处都不是"算不动"

| 现象 | 看着像 | 实际是 |
|---|---|---|
| `Aut(C_4 x C_4)` 报"建不出" | 96 阶的群太大 | **core 的 `multiply` 贵**：复合完再在 `\|Aut\|` 条 map 里线性搜一遍（`index.js:46326`），每次乘法 `O(\|Aut\| x \|G\|)` |
| `GL(2,4)` 报"本地建不了" | core 算不动 | **core 真没写这一族**：`createGL2(p)` 第一行就是 `if (!isPrime(p)) throw`，而 `createGroupFromSymbol` 的 switch 只硬编码了 `GL(2,2)` / `GL(2,3)` |

U47 划的那条"建群线 48"是**量错了对象**（当时看到 96 阶要 2.1s，就以为是"建群"本身贵）。

#### ① `Aut` 建群：把"线性搜"换成哈希乘法

给每张自同构 map 算一个签名（把 `G` 的元素 id 按序取像拼成串），建成 `签名 → 下标` 的哈希表。
乘法从"复合完再线性搜"降到 `O(|G|)`。

| 群 | `\|Aut\|` | core `createAutomorphismGroup` | `buildAutomorphismGroup` |
|---|---|---|---|
| `C_3 x C_3` | 48 | 181ms | **5ms** |
| `C_4 x C_4` | 96 | 2323ms | **13ms** |
| `A_5` | 120 | 21000ms | **106ms** |
| `C_2^3` | 168 | 60s 没完 | **33ms** |

- 删掉 `AUT_COUNT_CAP = 48`，换成 **`AUT_BUILD_BUDGET = 1_000_000`**，判据是 **`|Aut|² x |G|`**
  —— 这才是"全表闭包自校验 + 贪心挑生成元"的真实代价；
- 建群之前**先验后建**：全表闭包与求逆都落得回这堆自同构里才动手，否则返回 `null`
  （并报"自同构集不自洽"——那是**内部异常**，不是"算不动"）；
- 搜索那条线**没动**（`AUT_SEARCH_BUDGET = 30_000`）：`S_6` 的 18000 组确实搜不完，
  它继续由结论表接手（`|Aut(S_6)| = 1440`）。

**误伤检查**（写进回归）：`Aut(S_4)` = 24 · `Aut(C_3 x C_3)` = 48 · `Aut(D_8)` = 32 照旧**真算**
（元素是自同构本身，结论区才能说 `Aut(S_4) ≅ S_4`）；`S_6` 那一档仍旧走表。

#### ② `GL / SL / PGL / PSL`：新增 `gal/matrixGroups.ts`

core 把下面九个常见记号**全**标成 `backend`（真跑 `parseGroupNotation` 得到）：

| 记号 | 阶 | 耗时 | 生成元 |
|---|---|---|---|
| `GL(2,4)` | 180 | 3ms | 4 |
| `GL(2,5)` | 480 | 5ms | 3 |
| `GL(2,7)` | 2016 | 16ms | 4 |
| `GL(3,2)` | 168 | 2ms | 4 |
| `SL(2,4)` | 60 | 0ms | 3 |
| `SL(2,5)` | 120 | 1ms | 2 |
| `SL(2,7)` | 336 | 3ms | — |
| `PSL(2,7)` | 168 | 3ms | 2 |
| `PGL(2,7)` | 336 | 6ms | 3 |
| `PSL(2,5)` | 60 | 1ms | 2 |

**一行数学没抄**：矩阵乘、行列式（高斯消元，顺带判 `det != 0`）、求逆（高斯-约当）全是定义。
唯一要"造"的是有限域：`F_p` 用取模；`F_4 = GF(2)[x]/(x^2+x+1)` 用异或加、按 `w² = w+1` 乘。

四条纪律：

1. **生成元自校验**：core 把 `a = [[1,1],[0,1]]`、`b = [[0,1],[1,0]]` 写死了（`index.js:2119`）
   且**不检查**这两个能不能生成整个群。这里候选取初等矩阵 `E_ij(a)` 与 `diag(a,1,..)`，
   逐个加进生成元集并**重算闭包**，覆盖不满全群就返回 `null`（U49 同一条纪律）；
2. **只补 core 真没实现的族**：`GL(2,2)` / `GL(2,3)` / `SL(2,3)` core 自己建得出 ⇒ 一律 `null`
   （同一个记号不许长出两个只是同构的群对象）。这条**由函数自己守**；
3. **不猜**：域不支持（`F_8`/`F_9` 要挑不可约多项式）、结果阶超限（`GL(3,3)` = 11232）一律 `null`；
4. **商自己算**：core 的 `computeQuotientGroup` 开头就读 `subgroup.isNormal`（而
   `subgroupFromElementIds` 的 `isNormal` 恒 `false`，U40 记过这个坑），更要命的是**慢**
   —— `PGL(2,7)` 实测 **19.5 秒**。`quotientGroupOf` 自己按 `O(|G| x |Z|)` 开陪集，降到 **6ms**。

**这一批唯一的真 bug（改了两轮才找对）**：`PSL(2,7)` / `PSL(2,5)` 一开始判成"建不出"。
根因是 `PSL = SL / (Z ∩ SL)`，而 `det(aI) = a²` —— 只有 `a² = 1` 的那几个标量才落在 SL 里
（`q = 7` 时是 `±I`）。拿全部 `q-1` 个标量去乘，会写进一堆**根本不在 SL 里**的矩阵；
不筛的话 `cosetOf.size != mats.length`，下一步的相等检查就把 `PSL(2,7)` 判成"建不出"。
加一行 `const inMats = new Set(mats.map(keyOf))` 只在 `inMats.has(k)` 时写入 ⇒ 3ms / 1ms。

### 6.35 第三十一批做了什么（U51，2026-10-02）—— 半直积 `⋊`：记号欠定时的三态分诊

#### 起因：两句话都是错的

用户两张截图，一句追问：

> 「所以到底是什么？`GL(2,Z/4Z)`，`(C2)^4⋊S3` 算不出来？」
> 「群作用，半直积，什么时候接入画布？」

分诊出**三件不同的事**，只有第二、三件是这一批的活：

| 输入 | core 的回答 | 真相 |
|---|---|---|
| `GL(2,Z/4Z)` | 「该记号本地建不了」 | **对**，但理由不同：`Z/4Z` 是**环**不是域，`matrixGroups.ts` 那一族只做域（`F_p` / `F_4`）⇒ **族外，本批不管** |
| `C_2^4 : S_3` | 「**找不到**满足条件的非平凡作用 φ」 | **这句话是错的**。非平凡作用一抓一大把（坐标写法 16800 种）—— core 把「**不唯一**」说成了「**不存在**」 |
| `C_2^2 : C_3` | 同上 | 非平凡作用**唯一**（两个 3 阶选取共轭）⇒ 群**唯一**（= `A_4`）。有解被报成无解 |

第三件最刺眼：用户连「该填什么」都不知道，因为系统说"没有"。

#### 方向定案：计算器，不是可视化

用户当场把方向钉死：

> 「目前在做计算器，**不是可视化**！」

引擎（`@groupviz/react`）导出的 `ActionScene` / `SceneWindow` **一个都不接** ——
`⋊` 是**算**出来的东西，不是画出来的东西。这一批只把「算」做完、把结果显示清楚。

#### 三态分诊（`gal/semidirect.ts`）

`Hom(H, Aut(N))` 的枚举：拿 H 的**生成元**的像在 H 上 BFS 传播，**一致性检查（同一元素两条字路径必须给同一个像）就是"φ 是同态"的充要判据**；得出的群按**群指纹**归并。

| 态 | 判据 | 界面上说什么 |
|---|---|---|
| `ok` | 作用**唯一** | 直接建，副行 `\|G\| = n，作用唯一` |
| `multi` | 多个**本质不同**的作用 | **红字**「`X` 与 `Y` 的忠实作用有 **3** 个本质不同的选法……**它不是一个群**」+ 候选用**不变量**列出 |
| `trivial` | 只有平凡作用 | 绿字建出来，副行「只有平凡作用，**就指直积**」（说清，而不是让人以为算不出来） |
| `blocked` | 算不动 / 超线 | 红字说清**卡在哪一步**（"`Aut(C_2^5)` 要逐个同阶元素试 28629151 x 32 次，本地不跑"） |

**候选必须两两分得开**：同一个记号下不同作用的群，符号长得**一模一样**
（都是 `C_{2}^{4} \rtimes_{\phi} S_{3}`）—— 光列符号等于没列。指纹取
**`阶 | 交换 | |Z| | |[G,G]| | 阶分布`**，`C_2^4 : S_3` 那三类的 `|Z|` 正好是 4 / 2 / 1。

#### 忠实 / 非忠实**双桶**（本批核心判据）

`N ⋊_φ H` 对**任意**同态 φ 都有定义，所以 φ 非单的那些也是合法解；
但 φ 非单时「H 其实没整体动起来」（`ker φ` 直接成了直积因子）。

判据：**先忠实，忠实的没有才退非平凡**。

写反了会怎样：`C_2^2 : C_4` 根本不存在忠实作用（`C_4` 嵌不进 `GL(2,2)`，`|GL(2,2)| = 6`、`gcd(4,6) = 2`），
若判成"没忠实的就指直积"，它会变成 `C_2^2 x C_4` —— 而**光看阶分布分不开这两个群**
（都是 `1/7/8`），得再上 `|Z|`（半直积 4 / 直积 16）与交换性。实测踩过这个坑，双桶就是为它改的。

`Aut(C_2^n) = GL(n,2)` 走**本地 F₂ 矩阵枚举**：core 的 `AUTOMORPHISM_MAX_COMBINATIONS = 30000`
是照"逐个同阶元素试"算的，`C_2^4` 的 `15^4 = 50625` **过不了它自己那道门**（实测 0ms 回空数组），
而 F₂ 上的 4x4 可逆矩阵只有 20160 个。

#### 内半直积：用户问"什么时候接入画布"的正解

记号层面的欠定是真的（`C_2^4 : S_3` 谁都定不下 φ）。但**画布上的操作不是记号**：

从那个 96 阶群 `G` 里挑出两个子群 `N`、`H` 拉一条线时，`⋊(N, H)` 指的**就是 `G` 自己** ——
作用 φ 是 G 内部的共轭，**存在且唯一**。这时"选哪个作用"不是用户要做的决定。

判据三条（`planInnerSemidirect`）：`N ⊴ G` · `N ∩ H = 1` · `|N| x |H| = |G|`。
正规性走**逐生成元共轭**（`O(生成元个数 x |N|)` 次乘法，任意阶精确），
**不借** `relations.ts` 的 `findAllNormalSubgroups`（那条路在 144 阶以上直接不判）。

不成立时**必须披露**（换群不说明就是**静默改题**）：

| 不成立的那一条 | 副行 | `note` |
|---|---|---|
| `\|N\| x \|H\| != \|G\|` | 按外半直积算（作用唯一） | `x` 与母群的 `y` 阶不等，乘不出整个母群 |
| 交不平凡 | 同上 | 两边相交于 `k` 个元素，不是平凡交 |
| 左边不正规 | 同上 | 左边那个在母群里不正规；**右边那个反过来正规，两个参数对调即可** |

两个**各造各的**的群（没有共同母群）不是"内半直积不成立"，是"这条路不适用" —— 不多嘴。

#### 接线：四个入口自动获得

| 那一处 | 做了什么 |
|---|---|
| `ops.ts` | 新增 `semidirectProduct` op。中缀**只收 `\rtimes`，不收 `:`** —— `:` 那个形态由记号层分诊接，两条路共用同一个 `planSemidirect` |
| `evalDef.ts` | 记号层（`N : H`）走三态分诊；报错措辞**只用用户敲的原文**（`canonical` 是 core 归一后的 `C_{2}^{4}`，带花括号，摆到纯文本面上就是乱飞） |

### 6.36 第三十二批做了什么（U52，2026-10-02）—— 自定义作用：`ActionKind` 里最后那个空槽

#### 起因：五个字

> 「自定义群作用呢？」

侦察下来的事实很短：`value.ts` 里 `custom` **有标签、有分支、零个生产者**（全项目 `grep` 得 0），
而四个内置作用（共轭 / 左正则 / 陪集 / 共轭在子群集）早就接线了 —— ⑪ 那一条的第三项一直挂着。

代数上这件事有个干净的入口：**一个作用就是一个同态 `φ : G -> S_Ω`**，
而 `S_Ω` 的元素本身就是 Ω 上的置换。所以「定义作用」= 「给每个生成元挑一个置换」：
与「映射」是同一件事，只是**靶群不必真建出来**（`n` 一点，`S_n` 就在那儿）。

#### 用户拍板的两条

| 问题 | 选项 | 拍板 |
|---|---|---|
| 做到哪一步 | A 只加 op ／ **B op + 作用编辑器** | **B** —— 菜单、⊕ 球、文本三条路都通，⑪ 才算真销账 |
| 输入形态 | 从靶群 `S_n` 下拉选元素 ／ **循环记号文本** | **循环记号文本**：① 与显示形态一致（屏幕上写着 `(1 2 3 4)`，用户就能照着敲回来）· ② `n` 不受任何群构造上限的约束（换成"靶群取 `S_n`"就得 `S_n` 建得出来才行）· ③ core 的 `parseCycleNotation` 现成 |

#### 内核（`gal/customAction.ts`）：五道门 + 一次披露

`planCustomAction(G, n, drafts)` 是 op 与编辑器**共用**的那一个函数 —— 所以"边填边看到的"
与"确认后算出来的"不可能不一致。分诊顺序（每一道都在**调用前**）：

| # | 门 | 判据 / 常量 |
|---|---|---|
| ① | n 合法 | 正整数 |
| ② | 点数上限 | `CUSTOM_ACTION_POINT_CAP = 400`（不是"算不动"，是**手写记号**的边界：400 个点没人真去敲，超线多半是打错了 `n`）|
| ③ | `\|G\| x n` 上限 | `CUSTOM_ACTION_CELL_CAP = 100_000`（实测锚点：`S_7` 自然作用 35280 → **97ms**、`S_6` → 5.5ms、`C_5000`(n=2) → 2ms）|
| ④ | 有生成元 | 「已知群」没有生成元表（U48）|
| ⑤ | **生成元可分** | `generatorsDistinct`（见下面那条真 bug）|
| ⑥ | 逐生成元的像 | 能解析成 Ω 上的置换（或 `e`）· **像的阶必须整除生成元的阶** |
| ⑦ | 缺像 | 少一个就报"还有 k 个生成元没给像" |
| ⑧ | 传播 | core 的 `extendAndVerifyPerms` —— **BFS 传播时的一致性检查就是"是同态"的判据** |
| ⑨ | 披露 | 忠实 / 不忠实 + 核的阶（**不是错误**）|

#### 三条纪律

① **不许静默补**。core 的 `buildActionComputation(G, {kind:'custom'})` 在**不给 arrows** 时
静默返回**平凡作用**（`isHomomorphism: true` + n 个单点轨道），而 `extendAndVerifyPerms`
少一个生成元的像就 **THROW TypeError**。两头都不能学 ⇒ "用户到底填了没有"必须自己数。

⚠️ 由此定了一条**看起来小、其实是核心**的约定：**恒等写 `e`，留空不算**。
core 的 `parseCycleNotation` 没有恒等的写法（`()` / `(1)` / `1` / `e` 全回 `null` ——
它只认"长度 ≥ 2 的循环"），所以恒等由应用层认 `IDENTITY_TOKEN = 'e'`；
而**留空 = 没填** —— 静默补一个恒等下去，用户会得到一个"看起来成功了、其实什么都没作用"
的平凡作用（核 = G），而且**看不出自己没填**。

② **忠实性必须披露**。`C_4` 把 `a` 映成 `(12)(34)` 是**合法作用**，但核是 `⟨a²⟩` ——
用户不该自己去猜这件事。新增共用判据 **`actionKernel(A)`**（映成恒等置换的那些元素），
**一处算、三处用**：

| 消费者 | 说什么 |
|---|---|
| op 的 `sub` / `note` | 副行 `\|Ω\| = n - 传递/轨道数 - 忠实／不忠实（核阶 k）`；不忠实时 `note` 补一句"像只有几阶" |
| 信息面板（新增一行「核」） | `忠实（只有单位元）` ／ `不忠实，阶 k` |
| 结论层（新增一条「同态的核」） | `\|ker φ\| = k`；忠实走 `note` 语气（弱化），不忠实走 `key`（头条）|

顺带把**四个内置作用的核各自点名**（同一个判据对它们一样成立）：
共轭作用 → **`Z(G)`** · 左正则作用 → `{e}`（**这就是 Cayley 定理**）· 陪集作用 → `H` 的全部共轭之交。

③ **预算守卫在调用前**（U47 立的规矩，同步求值没有"超时"这个选项）。

#### 编辑器（`ui/ActionBuilder.tsx`）

- 形态与「映射构建器」同款（都是"填生成元的像"），但多一个 `n`；
- **两个一键起点**：`平凡作用`（全填 `e`）· `左正则作用`（`n` 设成 `|G|`，按 `computeLeftTranslationPerms`
  填像 —— 对每个群都有定义且**必然忠实**）。它们把记号**写进输入框**给用户看见，
  不搞"留空就是恒等"那种静默默认；
- `App.tsx` 里按 op id 分派（`customAction` → `ActionBuilder`，其余 → `MapBuilder`），
  `editorNodes` 从"固定两个"放宽为**按 `inter.picked` 逐个找**（作用只要一个端点）；

#### 顺手抓到的真 bug：直积群的生成元在 core 里重名重号

`.tmp-u52/probe7.mjs` 实测：

| 群 | `gen.name` | `gen.symbol` | `el.id` |

| `C_2^2` | `a`, `a` | `1`, `1` | `e1\|e0`, `e0\|e1` |

`自定义作用(G, n, ...)` 的参数里夹着标量 `n`（`int`，画布永远给不了）⇒

### 6.37 第三十三批做了什么（U53，2026-10-02）—— 任意阶集合：点集构造器 + Ω 当参数

#### 起因：一句质问

> 「逗我吗，连任意阶集合都创建不了，怎么创建自定义群作用？你做了半天做了什么？」

#### 先验再答：三条硬事实

没辩解，直接`.tmp-u53/probe2.ts` 在语义层真跑：

| 写法 | 实测 |
|---|---|
| `{1,2,3}` | 「无法识别的群记号」 |
| `集合(1,2,3)` / `点集(5)` | 「没有这个操作」 |
| `底集(S)` | 要 `S` **已经存在**（子群集 / 元素集 / 群）|

⇒ **用户是对的**。唯一能造 `set` 的只有 `底集`，而它要求**集合的点从某个已存在的群里借**。

再往下一层才是根因：**U9「集合构造器」一直是"未做"**，而 U52 的作用编辑器**建在一个不存在的层上** ——
`自定义作用` 的第二参是个数字 `n`，Ω 永远是内核 `omegaOf()` 硬造的 `{1..n}`。

```
自定义作用(S_4, 底集(Syl(S_4, 3)), s12 -> (12))
  → 作用点集的基数 n 必须是正整数
```

#### 用户拍板：两条一起才闭环

| 问题 | 选项 | 拍板 |

`labelWritable` · `planCountPointSet(n)` · `planLabeledPointSet(labels)` · `resolvePointToken` ·
`labelCycleToNumeric` · `labelsHint`。

① **`GalSet.group` 放宽为 `Group | null`**（本批最要紧的一个字）。一批抽象点**不属于任何群**。
**不许**退化成"母群 = `C_1`" —— "没有母群"与"母群是平凡群"是两件事，
后者会把 `G 与 Ω 来自不同的群` 那道关也一起骗过。

**标签优先不能吃掉 core 自己的语法。**

④ **共用判据**：`omegaSpecOfValue` 一处供 op 与编辑器（"编辑器能填的"与"手打的能吃"必须是同一批）·

| 改动 | 判据 / 理由 |

#### 交叉核对（本批最硬的一条）

同一个作用两条路定义，**置换表必须逐项相同**：

```
builtin = 共轭作用在(S_4, 底集(Syl(S_4, 3)))
mine    = 自定义作用(S_4, 底集(Syl(S_4, 3)), s12 -> (1 4), c -> (1 4 3 2))
```
