## 0. 一句话

**把「一种表达形状」拆成「三种投影」**——对象表仍然只有一份，
`画布 / 工作台 / 草稿区` 是它的三条 `derive`，各有判据、各有产物形状。

现在的界面只有**一个投影**：45 条 op 全部编译成"一行 `H = closure(G, r)`"，
再由 `build.ts`（纯函数）派生成画布节点 / 边 / 面板。
这个设计很干净，但代价是**只有一种表达形状**——
而用户点名的那些东西（集合加结构 → 群、群同态、群作用、半直积、自同构、共轭类）
**天然不是"一行"**。

## 2. 三区是三种投影，不是三份数据

```
                    objects : GalObject[]        ← 唯一的一份
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
   homeOf(v) = 画布    homeOf(v) = 工作台   homeOf(v) = 草稿区
   顶点 / 边            表 / 档案            未成形 / 已弃
```

**为什么不能做成三份数据**：`identity.ts#callKey` 那条缺口⑯就是"同一对象认成两份"
（手打 `I = im(\varphi)` 与点 φ 悬浮球得到两个对象）。
草稿区尤其危险——它天然是"另一堆对象"。⇒ 三区必须共用对象表。

**判据只有一份**：`homeOf(value) → 'canvas' | 'bench' | 'draft'`，
**与 `sortOf` 同构、定义一次三处消费、判不出就回画布**。
（`sortOf` 已经回答"它在图里处于什么位置"，`homeOf` 答的是"它**该被谁**呈现"。）

### 2.1 三档的判据与产物

| 区 | 判据 | 典型对象 | 产物形状 |
|---|---|---|---|
| **画布** | 产物是**顶点或边**（`sortOf ∈ {vertex, edge}`）且**要与别的对象一起看** | `G ↷ Ω` · `ker` · `π` · `≅` · 同构定理的交换图 | 一个节点 / 一条箭头（**现有全部照旧**）|
| **工作台** | 产物是**表或档案**（要逐行读、要能引用） | 运算表 · 公理档案 · 生成元→像 · 置换表 · 共轭类 · 元素表 | **常驻结构化卡片**（不是一行文本）|
| **草稿区** | **尚未成形或已弃** | 试算中的表达式 · 失败尝试 · 分解与判定 · 序列 | 可回收的一行（**带"扶正"成对象的入口**）|

⚠️ **`list` / `scalar` 不等于"草稿区的东西"**。`Sub(G)`（子群集）已经在信息面板有家
（`sortOf = 'list'`），不是缺一个区。草稿区真正接的是**时间轴上的第三态**：
还没成形（试算）/ 算了但判定为不上画布（分解、序列）/ 废弃（算错了想留着回头看）。
现在这三者唯一的去处是"输入框一关就没"。

## 3. 工作台的槽位：**对象**，不是操作

### 3.1 为什么不按操作分槽

`docs/USABILITY.md` §0 的判语是"**先选操作，再点参数**，方向是反的"——
用户脑子里先有的是"把这两个凑一起"。
按操作分槽的工作台会退回那条路，只是把它平铺开。

### 3.2 槽位 = 对象

```
┌─ 工作台 ──────────────────────────────────────────┐
│  对象列表         │  选中对象的详情 + 可对它做的事   │
│  （复用 ObjectDock）│                              │
│    G = S_4        │  ┌ 结论区（identity / 阶 / …）│
│    N = ker f      │  ├ 元素表（逐元素一行）        │
│    Ac = conjAction│  ├ 运算表 / 公理档案           │
│    …              │  └ 可做的事（径向菜单那三层）  │
└───────────────────┴──────────────────────────────┘
```

**三个已有编辑器（`MapBuilder` / `ActionBuilder` / `StructureBuilder`）形态高度同构**：
源 + 参数 + 逐项填 + **产出一行定义**。它们是**同一个组件的三个配置**，
工作台该把它们收成"对象详情的一个视图"，而不是三套独立弹窗。

### 3.3 输入输出的重新设计（用户明确点了这块）

| 现在 | 问题 | 工作台里 |
|---|---|---|
| 弹窗式编辑器盖住画布 | 填一半被误触（`App.tsx` 有特判）| 常驻卡片，不盖画布 |
| 表提交后消失 | 只能点开第三层面板再看 | 表就在那儿，可引用 |
| 报错语与结果分居两块 | 填错时不知道哪一行错了 | 逐行内联报错（`MapBuilder` 已有 `violation` 的定向提示，搬到行上）|
| 结论是一行字 | 引用不了 | 结论块 + 「照抄这一步」（`OpDef.notation` 已经是函数式，见 U54）|

## 4. 布局：**画布为主 + 两个抽屉**，不是三栏并排

现有 v3 决策（`INTERACTION.md` §5）已定死"**画布不给抽屉让位**"。
三栏并排会**直接杀掉交换图**——`tikz-cd` 那种图就是要宽的，
而 `DIAGRAM_SPEC` 的硬约束（落格点 / 水平同高 / 垂直同列）已经把宽度用掉了。

| | 三栏并排 | 画布为主 + 工作台/草稿做抽屉（**建议**）|
|---|---|---|
| 好处 | 都在眼前 | 不动现有决策；抽屉可收可放 |
| 坏处 | 画布宽度掉一半 | 工作台不能"永远在眼前" |
| 风险 | 违反 `INTERACTION` §5 已定决策 | —— |

> ⚠️ **窄窗（≤1080px）的老问题会变严重**：现在已经是 5 个抽屉挤在一角。
> 三区之后建议**任一时刻只开一个**（工作台开着时草稿区自动收）。

## 5. 草稿区：两条候选判据（**待用户拍板**）

| 候选 | 收什么 | 现状缺口 |
|---|---|---|
| **A · 尝试存档** | 还没成形的表达式、失败的尝试、算错了想回头看的 | 现在输入球一关就丢（`HISTORY` 里"草稿画布"从 U21 挂到现在没兑现）|
| **B · 不上画布的对象** | 分解（`G ≅ N ⋊ H`）/ 判定 / 序列 —— 算得出但没有节点形状 | 现在只是信息面板里一行字 |

**倾向 A**，理由：

- B 的判据**站不住**：`subgroups`（子群集）不在画布上，但它**已经有家**
  （`sortOf = 'list'` ⇒ 信息面板 list 档），不是"缺一个区"。
  B 唯一真正的缺口是**分解文本**（`G ≅ A_4 ⋊ C_2`）——
  而它更适合进**工作台**（结论块，可照抄），不是草稿区（垃圾桶）。
- A 解决的是**当前确实在流血**的问题：`HISTORY` 记着"草稿画布（用户构思）"，
  而用户刚做完一张图刷新一下试算就没了（`USABILITY` ⑫ 只想解决"定义行丢"，
  试算过程仍然丢）。

**草稿区不是垃圾桶**——如果采用 A，必须有一条纪律：**草稿区里的东西要能一键"扶正"成对象**，
否则它会变成什么都往里扔、进去就找不回来的地方。
