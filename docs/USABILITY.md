# 可用性审计（用户视角）

> **本文件是现状审计**：用户想做某件事时最可能的动作是什么、那条路通不通、哪里会卡住。
> 每一次修复的**详细过程**（改法 / 断言 / 教训）在 [HISTORY.md](HISTORY.md) 丙编，不在这里复述。
> 两者的边界与写入纪律见 [docs/README.md](README.md)。
>
> ⚠️ **操作名的读法（U54，2026-10-03 起）**：全部 op 名统一成 **ASCII 英文**，中文别名已删。
> 本文件 U54 之前的条目里的中文 op 名是历史记录，**不要照抄**；现行写法看 [`../README.md`](../README.md)。
>
> **问题不是"能不能算"，而是"用户会怎么做、那条路通不通"。**
> 与 [TASKS.md](TASKS.md) 互补——那份是"输入视角"（这行定义能不能算），
> 这份是"**动作视角**"（用户想到这件事时，手往哪儿放）。
>
> 数据来源（都是实测，不是推理）：
> - **可点性地图**：`opsFor` / `singleOpsFor` / `multiOps` 是纯函数，直接枚举每种"选中"给出的候选
> - **任务重跑**：`docs/TASKS.md` 那份清单按输入逐条重跑
> - **真浏览器走查**：`apps/web/verify/e2e/`（交互层）

## 0. 一句话结论

**数学能力已经不缺（2026-09-25 审计时：55 条里 45 条能算），缺的是"路"。**

审计当时有三个操作入口（左栏表 / 对象悬浮球 / 多对象球 ⊕）**本质是同一个模式的三种外壳**：
**先选操作，再点参数**。而用户脑子里先有的是**"把这两个凑一起"**——这条方向的路没有。
于是凡是要"关联两样东西"的意图（`f(H)`、`H ⊆ G`、`K ⊴ S₄`），一律只能打字；打不出来就卡死。

> **后续**：第四条路已经补上（U21 拖拽连线：拖 A 到 B 松手 → "这两个能做的事"），
> §2.2 / §2.3 / §3.C 的那些 ❌ 逐条修完（U19–U21）；U27 又把 core 里"能算但没接"的一批接上了。

## 1. 三条路径的现状

| 路径 | 用户怎么做 | 现状 | 代价 |
|---|---|---|---|
| **打字** | 点 `✎` → 手写 `K = ker(f)` | 最可靠，覆盖注册表全部 38 条操作 | 要记住操作名（U25 起输入只认 ASCII，`\varphi` 这类写法面板上随处可抄） |
| **选操作 → 点参数** | 球 / ⊕球 → 选操作 → 点对象 | 通（`opsFor` 保证候选与可点一致） | **方向反了**；且"不上画布的对象"选不到 —— 后者已由**对象列表行上的「操作」**补上（U21 加在信息面板、**U44 挪到行上**） |
| **直接操作对象** | 拖 A 到 B、拉连线 | ✅ **U21 落地**（唯一候选直接执行，多个弹菜单） | —— |

## 2. 可点性地图（实测：选了什么，能点到什么）

> 下表是 **U27 后重跑的实测值**（`opsFor` / `singleOpsFor` / `multiOps` 都是纯函数，直接枚举）。

### 2.1 能点到的

| 选中 | 球里能点到 | 条数 |
|---|---|---|
| 一个群 | 共轭作用 · 正则作用 · Aut · 底集 · Z · **Inn** · Sub · **极大子群** · pSub · Syl · 正规子群 · [G,G] · 闭包 · ord | **14** |

### 2.2 曾经"点不到"的组合 —— ✅ U20/U21 已修

| 组合 | 审计时 `opsFor` 结果 | 现在 |
|---|---|---|
| **映射 + 群** | **空** | ✅ `像(f, H)`（U20）—— **拖 H 到 f 上**还会唯一候选直接执行（U21） |
| **映射 + 子群** | **空** | ✅ 同上 |
| 群 + 群 | × · 映射 | ✅ 合理（`商` 要求第二个是子群；`包含` 两个方向各实判一次） |

### 2.3 曾经选不到的**对象** —— ✅ U21 补了入口

`subgroups`（子群集）与 `elements`（元素集）按存在层级是 `list` —— **不上画布**，
所以**用户根本选不中它们**。U21 曾在信息面板加一行**「可做」**（`singleOpsFor`）补入口；
**U44 把那行砍了，入口挪到「操作」抽屉里那个对象所在的行上**（行右侧的「操作」按钮）：

| 想做的 | 数据上支持吗 | 现在 |
|---|---|---|
| `Syl(G,3)` 之后要 `Ω = 底集(S)` | ✅ `opsFor([subgroups])` 给出「底集」 | ✅ **对象列表行上的「操作」**直接点（U44；判据 `sortOf === 'list'`） |
| `Sub(G)` 之后要 `闭包(S)` | ✅ 同上 | ✅ 同上 |
| 从子群集里挑一个当对象 | ✅ 信息面板有「取出为对象」 | ✅ |

**这是本审计最实的一条发现**（也是 U21 的全部动机）：不是操作不够，是**中间产物没有操作入口**。

## 4. 输入契约的破口

| 现象 | 实测 | 性质 |
|---|---|---|
| **φ 敲不出来** | `checkName('\phi')` → `ok:false`（"名字只能用字母（含希腊字母）/ 数字 / 下划线 / 中文"）；字符 `φ` 本身合法 | 系统在模板里写 `φ = 映射(...)`，用户却敲不出——**违反"展示成什么样就得能照着敲回去"这条契约** |
| 操作名当群记号解析 | 打 `极大子群(G)` → 报"无法识别：极大子群(G)｜无法识别的群记号 …可用写法：C₁₂ · S₃ · D₄ ……" | **完全误导**：用户会以为要输群记号 |
| 关系写成 `⊆` | 打 `H ⊆ G` → 报"缺少「=」" | 用户写的是关系，系统当成漏了等号 |
| 未支持 vs 打错字 | `Burnside(A)` / `gcd(12,18)` / `φ(12)` 与"手滑打错"给**同一句**报错 | 用户分不清"没这个功能"还是"我打错了" |

> **四条都已修**（U18 修报错文案，U25 定下"输入只认 ASCII"的形态；U27 把 `gcd` / `Burnside(A)` 变成真操作）。
> 保留在这里是因为它们是"输入契约"这一层的**原始病历**：以后出现"用户敲不出来 / 报错答非所问"，
> 先回来看这四条的形状。

## 5. 结论区的沉默规律（"K 是什么"的根因）

实测 `groupInsights` 对几个典型对象：

| 对象 | 符号 | 识别结果 | 结论条数 |
|---|---|---|---|
| `G = S_4` | `S_{4}` | `S_{4}` | 1（只有"阶"） |
| `Q = 商(G, N)` | `S_{4}/N` | `S_{3}` | **2（同构 + 阶）** ✅ |
| `K = ker(f)` | `C_{2}` | `C_{2}` | 1（只有"阶"） |
| `H = 闭包(G, r)` | `C_{4}` | `C_{4}` | 1（只有"阶"） |

**规律**：判据是"识别结果 ≠ 自身符号才说"。
- 商的符号是**构造记号**（`S₄/N`）→ 与识别结果不同 → **说话** ✅
- 核 / 像 / 子群的符号是**结构记号**（`C₂`、`C₂×C₂`）→ 与识别结果相同 → **永远沉默** ❌

而**结构记号恰恰是构造物的常态**。于是"K 是什么"这个问题，在系统里**没有地方回答**。
另外"基本"tab 的「识别」行依赖 `group.isoSymbol` —— 那是**只有从小群库建出来的群**才有的字段，
`createGroupFromSymbol` / `buildSubgroupGroup` 都没有 → **那行基本是死代码**。

> **U18 已修**（见 §6.1）：判据改成看 `node.opId` —— 由操作构造的一律说，并给 SmallGroup 编号与惯用名；
> 那行死代码删了。这一节保留为"当初为什么会沉默"的**根因记录**（U19 的关系层也沿用了同一条"看它怎么来的"判据）。

### 三条教训

- **回归线是资产，不是临时物。** U10（格点 / 拖动 / 吸附 / 钉住）当年的走查是**临时脚本**，跑完就扔；
  到 U21 动指针手势时，**谁也说不出它有没有被碰坏**。临时脚本不算回归 —— 入库才算。
- **判据必须在失败时会变红。** `e2e/third-iso.mjs` 曾有条**恒真断言**（读 `.row-err` 判整段成功，
  而失败的行根本进不了对象表 ⇒ `.row-err` 恒空），那段哪怕全挂也报 PASS。**已换成读画布节点 + 点开看识别。**
- **"入口通了" ≠ "进去能用"**（U58，`verify/README.md` 第 74 条）：补完入口必须
  **以用户的手把全程走一遍**（起点 → 产物 → **产物上能看到什么**），并把"产物那一侧"单独写一套走查。
