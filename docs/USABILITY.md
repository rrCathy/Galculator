# 可用性审计（用户视角）

> **问题不是"能不能算"，而是"用户会怎么做、那条路通不通"。**
> 这份审计换了提问方式：对每一件用户想做的事，先问**他最可能的动作是什么**（打字？点球？拖？），
> 再实测那条路。与 [TASKS.md](TASKS.md) 互补——那份是"输入视角"（这行定义能不能算），
> 这份是"**动作视角**"（用户想到这件事时，手往哪儿放）。
>
> 数据来源（都是实测，不是推理）：
> - **可点性地图**：`opsFor` / `singleOpsFor` / `multiOps` 是纯函数，直接枚举每种"选中"给出的候选
> - **任务重跑**：`docs/TASKS.md` 那份清单按输入逐条重跑（原脚本在已删的 `.tmp-verify/` 里，本次重写）
> - **真浏览器走查**：`apps/web/verify/e2e/`（交互层）
>
> 探针在 `apps/web/.tmp-probe/`（临时目录，结论在这里）。

## 0. 一句话结论

**数学能力已经不缺（2026-09-25 审计时：55 条里 45 条能算），缺的是"路"。**

审计当时有三个操作入口（左栏表 / 对象悬浮球 / 多对象球 ⊕）**本质是同一个模式的三种外壳**：
**先选操作，再点参数**。而用户脑子里先有的是**"把这两个凑一起"**——这条方向的路没有。
于是凡是要"关联两样东西"的意图（`f(H)`、`H ⊆ G`、`K ⊴ S₄`），一律只能打字；打不出来就卡死。

> **后续**：第四条路已经补上（U21 拖拽连线：拖 A 到 B 松手 → "这两个能做的事"），
> §2.2 / §2.3 / §3.C 的那些 ❌ 逐条修完（U19–U21）；U27 又把 core 里"能算但没接"的一批接上了。

## 1. 三条路径的现状

| 路径 | 用户怎么做 | 现状 | 代价 |
|---|---|---|---|
| **打字** | 点 `✎` → 手写 `K = ker(f)` | 最可靠，覆盖注册表全部 38 条操作 | 要记住操作名（U25 起输入只认 ASCII，`\varphi` 这类写法面板上随处可抄） |
| **选操作 → 点参数** | 球 / ⊕球 → 选操作 → 点对象 | 通（`opsFor` 保证候选与可点一致） | **方向反了**；且"不上画布的对象"选不到 —— 后者已由「可做」一行补上（U21） |
| **直接操作对象** | 拖 A 到 B、拉连线 | ✅ **U21 落地**（唯一候选直接执行，多个弹菜单） | —— |

## 4. 输入契约的破口

| 现象 | 实测 | 性质 |
|---|---|---|
| **φ 敲不出来** | `checkName('\phi')` → `ok:false`（"名字只能用字母（含希腊字母）/ 数字 / 下划线 / 中文"）；字符 `φ` 本身合法 | 系统在模板里写 `φ = 映射(...)`，用户却敲不出——**违反"展示成什么样就得能照着敲回去"这条契约** |
| 操作名当群记号解析 | 打 `极大子群(G)` → 报"无法识别：极大子群(G)｜无法识别的群记号 …可用写法：C₁₂ · S₃ · D₄ ……" | **完全误导**：用户会以为要输群记号 |
| 关系写成 `⊆` | 打 `H ⊆ G` → 报"缺少「=」" | 用户写的是关系，系统当成漏了等号 |
| 未支持 vs 打错字 | `Burnside(A)` / `gcd(12,18)` / `φ(12)` 与"手滑打错"给**同一句**报错 | 用户分不清"没这个功能"还是"我打错了" |

> **四条都已修**（U18 修报错文案，U25 定下"输入只认 ASCII"的形态；U27 把 `gcd` / `Burnside(A)` 变成真操作）。
> 保留在这里是因为它们是"输入契约"这一层的**原始病历**：以后出现"用户敲不出来 / 报错答非所问"，
> 先回来看这四条的形状。

## 5. 结论区的沉默规律（"K 是什么"的根因）

实测 `groupInsights` 对几个典型对象：

| 对象 | 符号 | 识别结果 | 结论条数 |
|---|---|---|---|
| `G = S_4` | `S_{4}` | `S_{4}` | 1（只有"阶"） |
| `Q = 商(G, N)` | `S_{4}/N` | `S_{3}` | **2（同构 + 阶）** ✅ |
| `K = ker(f)` | `C_{2}` | `C_{2}` | 1（只有"阶"） |
| `H = 闭包(G, r)` | `C_{4}` | `C_{4}` | 1（只有"阶"） |

**规律**：判据是"识别结果 ≠ 自身符号才说"。
- 商的符号是**构造记号**（`S₄/N`）→ 与识别结果不同 → **说话** ✅
- 核 / 像 / 子群的符号是**结构记号**（`C₂`、`C₂×C₂`）→ 与识别结果相同 → **永远沉默** ❌

而**结构记号恰恰是构造物的常态**。于是"K 是什么"这个问题，在系统里**没有地方回答**。
另外"基本"tab 的「识别」行依赖 `group.isoSymbol` —— 那是**只有从小群库建出来的群**才有的字段，
`createGroupFromSymbol` / `buildSubgroupGroup` 都没有 → **那行基本是死代码**。

> **U18 已修**（见 §6.1）：判据改成看 `node.opId` —— 由操作构造的一律说，并给 SmallGroup 编号与惯用名；
> 那行死代码删了。这一节保留为"当初为什么会沉默"的**根因记录**（U19 的关系层也沿用了同一条"看它怎么来的"判据）。

### 6.2 U19 做了什么（2026-09-25）—— 关系层

**新增 `gal/relations.ts`。** 关系的来源**只有两条，都不猜**：

| 来源 | 覆盖什么 | 例（实测） |
|---|---|---|
| **① 由来源决定**（`node.sources` + `node.opId`） | `ker` / `im` / `Z(G)` / `C_G(S)` / `N_G(H)` / `[G,G]` / `⟨S⟩` / `A∩B` / `商` | `K = ker f ⊴ S₄ · 指数 [S₄:K] = 24 / 4 = 6` |
| **② 元素集包含**（`containment()`，三道关） | **两个各自独立声明的群之间** | 手打 `A_4` 与 `S_4` → `A₄ ≤ S₄` · ⊴ 正规 · 指数 24 / 12 = 2 |

包含判定的**三道关**（`containment()`）：

1. `H` 的每个元素 id 都能在 `G` 里找到（id 空间一致）
2. `subgroupFromElementIds(G, ids)` 认可（含单位元 + 乘法封闭）
3. 校验出的子群阶 **= `|H|`**

再拿 `findAllNormalSubgroups(G)` 判 ⊴（按 `subgroupSetKey` 比对，超枚举守卫则不判定）。

**为什么必须这么严**（实测，两条都是假阳性陷阱）：

| 陷阱 | 现象 | 挡住它的是 |
|---|---|---|
| `V₄` vs `D₄` | `subgroupFromElementIds(D_4, ['e','a','b','c'])` **不报错** —— 它把认不得的引用一丢了之，返回**平凡子群** → 朴素写法得出 `V₄ ≤ D₄` | 第 ① ③ 关（V₄ 的 id 是 `e a b c`，D₄ 的是 `r0…s3`，一个都找不到） |
| `C₂` vs `C₄` | id 是**真前缀关系**（`e0 e1` ⊂ `e0 e1 e2 e3`），第 ① 关**会通过** | 第 ② 关（`e1 + e1 = e2 ∉ {e0,e1}`，乘法不封闭） |

**三条纪律：**

- **指数 1 单列成「同一」** —— `[G:K] = 1` ⟺ 元素完全相同 ⟺ 同一个群。
  `ker f` 与 `闭包(G, (12)(34), (13)(24))` 都是 V₄、元素 id 一模一样；
  两个各自声明的 `C_6` 也一样（同一批 `e0…e5`）。写成一对"互为指数 1 的子群"会被读成两个东西。
- **假阳性必须为 0** —— 上面那张表的两条都写成了断言。
- **边界写在面板上** —— 那一节只列「已经建出来」的对象之间的关系，末尾一行明说；
  免得被读成"全部关系"（与 U18 给子群 tab 加"共轭类代表"是同一个教训）。

**面板落点**：信息面板在**结论层与 tab 之间**插一节「关系」。每行 = 类标签（核 / 像 / 商 / 同一 / 子群 / 包含 / 派生）
+ 关系式（KaTeX）+ 附注（记号对照 · ⊴ 正规 / 非正规 · 指数手算式）。每类有上限，截掉的只说个数。
反向给「派生」：**点画布上的箭头 `f`**，就能看到它长出了 `K = ker f`。

**与"拉箭头"的边界**：这一批是**把关系说清楚**（文字 + 手算数字，可点、可核）。
画布上真的长出那根箭头，是下一批（`包含(H, G)` 操作 + `relation` 值类型）。

### 6.3 U20 做了什么（2026-09-25）—— 子群像 + 声明包含

用户原始投诉的 ③④ 两条，都是"想做但没这个功能"。**走的是 (a)：做成操作**（而不是纯手势）。

| 操作 | 怎么写 | 关键设计 |
|---|---|---|
| **子群像** | `像(f, H)`（`H ≤ 定义域`） | 与 `像(f)`（整个像）**同一个 op** 的可选第二参——用户嘴里都叫"像"，别名只该指向一条路 |
| **声明包含** | `R = A ⊆ B` / `A⊆B` / `包含(A, B)` | **新值类型 `relation`**，`sortOf → edge`（是边不是顶点）→ 自动获得三个入口、可点选、可删、可进证明模板 |

**判据同源**：`包含(H, G)` 用的是 U19 那份 `containment()`（三道关）。于是"声明出来的关系"与信息面板里"算出来的关系"**永远一致**，不会出现两种说法。

**正规性不是声明的，是算出来的**：用户只说 `⊆`；`⊴` 由工具现场判。所以没有"声明正规子群"这个操作，也无从撒谎。非正规的 `↪`、正规的 `⊴`，画布上一眼可分。

**拦得住假声明**（每一条都给了理由，且都是**输入层**就拦）：

| 写法 | 报什么 |
|---|---|
| `D ⊆ G`（D₄ vs S₄） | 「D」不是「G」的子群 · 元素不是子集，或对乘法不封闭 |
| `X ⊆ Y`（C₂ vs C₄，id 是真前缀） | 同上（挡住它的是乘法封闭） |
| `X ⊆ Y`（C₄ ⊆ C₂，阶反了） | \|X\| = 4 > \|Y\| = 2，不可能是它的子群 |
| `X ⊆ Y`（两个 C₆，元素完全相同） | 元素完全相同，就是同一个群（包含是严格小于） |
| `A ⊆ K9`（K9 打错） | 「K9」算不出来：无法识别：K9 ← 这条**不再**答非所问地说"这行写的是一个关系" |

**顺带修掉一个布局老 bug**（U20 之前就有，只是新功能让它变得容易撞上）：
两条水平边**共用一个端点**时（`A ⊆ G` 与 `G → f → S₃`），老的列序规则"把夹在中间的组挪到行尾"会自相打架 ——
满足一条就把另一条弄坏。实测 `psi: B→G` 从 `H` 身上横穿过去，违反 DIAGRAM_SPEC §1.2。
新规则：把水平边当约束图，**分量内穷举列序，取"被夹住的边最少"的那个**；并列只接受严格更优（布局要稳）。
`H·G·B` 于是排成一条链。

### 6.5 U21 做了什么（2026-09-26）—— 拖拽连线 + 面板「可做」

第四批：缺口 ⑩⑤，也就是那份审计里排在最前面的"根"——**三个操作入口原本是同一个模式

| 做了什么 | 要点 |

| **面板「可做」**（⑤） | 不上画布的对象**没有悬浮球**（球挂在节点/箭头上）→ 子群集 `Syl_p(G)` 根本点不出操作。信息面板加一行「可做」，列的就是现成的 `singleOpsFor`。**零新机制**，而 `Syl → 底集 → 共轭作用在` 那条链中间不必再打字 |

   于是"把 S₄ 拖到 S₃ 上"会列出一条点了必然报错的项 → 改成**两个方向各实判一次，判据定顺序**；
   以及下面那条类型拆分。
2. **`ParamType` 一型两用的账要还** —— 从前 `subset` 对**一切**数集回 true，而多数 op

### 6.8 U26 做了什么（2026-09-28）—— 结构伴生边的语义身份

缺口清单里最后一条"用户会撞上"的：画布上的 `π` / `π₁` / `↪` / `=` / `≅` 是
**操作的结构顺手长出来的箭头**（`alongsideEdges` + 轨道边），背后没有对象，
U3.1 的 `objectId` 那条路对它们根本不适用 —— 于是它们成了画布上唯一点不动的东西。
**默认示范页面上就有两条**（`O = Ω` 与 `N ↪ G`），一进页面就撞。

**为什么不是"升级成一等对象"**：一等对象意味着进对象表、能被引用、挂悬浮球、
列 `ker` / `im` —— 可伴生边不在对象表里，列出来的按钮**点了必然报错**。
所以走第三条路：给它一份**语义身份**（`StructuralEdge`：kind + 两端 + 一句话 +
就地算好的账），焦点走独立前缀 `struct:<边 id>`，信息面板单开一节「这条箭头」。

| 点开的边 | 面板说什么（全部手算核对） |
|---|---|
| `π : G ↠ G/N` | 自然投影（商映射）· 核 = N · \|Q\| = \|G\| / \|N\| · 满射 |
| `π₁ : A×B ↠ A` | 积投影 · 核 = 另一个因子 · 满射 |
| `H ↪ G`（含 `⊴`） | 包含 · 指数 [G:H] · 正规 / 非正规（走 `containment()`） |
| `Orb = Ω` | 相等 · \|Orb\| = \|Ω\| · **传递** |
| `G/ker φ ≅ im φ` | 同构 · 两边同阶 |

三条纪律（都写成了断言，见 `suites/structural.ts` 31 条 + `e2e/structural-edges.mjs` 34 条）：

1. **菜单不撒谎** —— 不是对象 → **不挂悬浮球**（走查钉住"点伴生边后球数为 0"）。
2. **判据同源** —— 指数与正规性与信息面板"关系"节用同一份 `containment()`；
   核与阶读操作已知的输入。
3. **视觉身份不变** —— 可点了，但**仍是蓝灰细线**：可点改的是"能不能被问账"，
   不是它在图里的分量。

**顺手修掉一个展示老毛病**：包含边的标签从前硬写 `\hookrightarrow`，于是
`Z(G) ⊴ G`、`ker f ⊴ dom`、`C₃ ⊴ S₃`、`im φ ⊴ C₆`（**交换群**的子群全正规）
这些定理级的正规包含全被画成普通单射，与面板说的"⊴ 正规"自相矛盾。
现在标签也由 `containment` 定。受影响的是**期望值**，逐条手算核对后更新。

**这一批逼出来一个潜伏真 bug**（值得单独立此存照）：`containment` 的缓存 key
只看 `symbol#order` —— 记号与阶相同的两个群（从记号建的 `C₂` vs 从 `C₄` 里摘
出来的 2 阶子群）会**串**。从前它只在用户点开面板时被调用，撞上的概率低；
这一轮让**画布派生**也要问包含关系，调用面一宽就露了。修法：key 加**元素 id
指纹**（且连着记号 —— `V₄` 与 `C₄` 的元素 id 恰好都是 `e0..e3`）。



### 6.9 U27 做了什么（2026-09-28）—— core 接线：判定与结构

缺口 ⑪ 的第一批。这张单子上挂的一直是**打字能打、系统答不出**的那类问题 ——
`gcd(12, 18)`、`phi(12)`、`Burnside(A)`、`极大子群(G)`、`Inn(G)`，
以及"这个群的合成列是什么 / 它是直积还是半直积"。答案早就在 core 里
（`computeSubgroupSeries` / `findSemidirectDecompositions` / `computeBurnsideCount` / 子群格），
缺的只是**接哪儿、怎么摆**。

| 做了什么 | 要点 |
|---|---|
| **六条新操作** | `gcd` · `lcm` · **`phi`**（欧拉函数，展示成 `\varphi(n)`）· **`轨道数(A)`** · **`极大子群(G)`** · **`Inn(G)`** |
| **Burnside 的"两条路"** | `轨道数(A)` 直接数轨道（本系统的 `computeOrbits`），再用定理 `(1/\|G\|)·Σ\|Fix(g)\|` 算一遍（core 的实现）—— 副行当场对账：`= 5（Burnside: 40 / 8 = 5 v）`，对不上就标 `x`。D₄ 的 40 是手算的：`\|Fix(g)\| = \|C_G(g)\|`，4 个反射各 4、r/r³ 各 4、r² 是 8、e 是 8 |
| **极大子群 = 格的覆盖边** | 用 `computeSubgroupLattice` 指向 G 的那些边；S₄ 得到 8 个（A₄ + 三个 D₄ + 四个 S₃），A₄ 得到 5 个（V₄ + 四个 C₃），Cₚ 得到 1 个（{e}）—— 产出 `subgroups`，每个都能「取出为对象」 |
| **Inn(G) 走第一同构定理** | `Inn(G) ≅ G/Z(G)`：商掉中心。产出的群对象元素就是陪集，结论层再识别它 ≅ 什么（`Inn(D₄) ≅ V₄`） |
| **「结构」节（基本 tab）** | 完美 · **合成列**（若尔当-赫尔德因子 + 条数，`S₄ = C₂·C₃·C₂·C₂`）· **导来列**（阶链 `24 > 12 > 4 > 1`）· **分解**（`S₄ ≅ A₄ ⋊ C₂`；**直积优先** —— `D₆ ≅ D₃ × C₂` 比 `C₆ ⋊ C₂` 更贴用户的问题；A₅ 这类单群直接说"不可分解"并点名理由） |

**两条守卫，都是"成本自己兜住"**（写成了断言）：

1. **「结构」节 `|G| ≤ 60` 自动算** —— 实测 S₅（120）一次 3 秒、A₅（60）250ms、C₃³（27）217ms，
   所以上限比 core 的枚举线 144 更紧；超限**明说没算**（"|G| > 60：合成列 / 结构分解未自动计算"），
   不显示半截答案。结果按**元素 id 指纹**缓存（U26 那条纪律）。
2. **`极大子群` 超 `ENUMERATION_LIMIT` 自己拦** —— core 的格在超限时**静默退化成 {e} 与 G 两点**
   （实测 216 阶群），照单全收会把**平凡子群**当成 G 的极大子群。这正是审计 §5 说过的
   "沉默的错答案"里最坏的一类：它看起来像答案。

**为什么结构节不放进结论层**：结论层是"一眼"（同构 / 第一同构定理，一条一行），
结构节是一节四行 + 附注；更要紧的是**成本** —— 结论层在对象被选中的瞬间计算，
而半直积分解要枚举子群（S₅ 3 秒扛不住）。放在「基本」tab、自带上限与缓存，才两头都不吃亏。

### 6.17 第十三批做了什么（2026-09-29）—— 记号串号：`C_3 ∩ C_7` 不能再给"三个元素"

用户原话：「我拿F21测试同构第二定理，结果C3∩C7只能得到一个元素集吗？不是子群后面怎么操作？」

实测（探针）：`K = C_3`、`M = C_7`（两张各自构造的记号群）做 `交`，从前给出的是 **3 个元素的"交集"**
（`e0 e1 e2`）—— 既不是子群、也不是真交集。根因：**记号群的元素 id 是群内编号**，
`C_3` 的 `e0 e1 e2` 在 `C_7` 的 `e0…e6` 表里"也有"，只按 id 判就把它们当成了同一批元素。
（U32 的对齐把这条放大了：它挑 `C_7` 当上下文群，"交集"于是更像真的。）

| 项 | 落点 |
|---|---|
| **`idsComparable`**（id 能不能直接对着读） | `parents.ts`：**同一个世界**（根相同）**或两边都是自证式 id**。自证式 = `id === value.join(',')` —— 置换群的 `1,2,3,4` 就是那个置换（所以 `A_4 ∩ S_4`、`A_4 ⊆ S_4` 照旧按 id 判 ✓）；而 `e0…` / `r0…` / `g0…` 只是群内编号，跨群会撞号 |
| **集合运算**（∩ ∪ ∖ ·） | `alignSetSide` / `sideIn` 的"原位"判据换成 `idsComparable`；全失败且**两边的根不是同一个群**时，报「不在同一个群里（两者没有共同的母群）」并指路（先放进共同的大群，再对它里面的子群做运算） |
| **`包含` / `像` / `商` / `陪集作用`** | 同一道检查（**陪集层除外** —— 跨商群那套按陪集成员语义走）：id 全在但不可对着读 → 专门措辞「两个各自构造的群，元素记号碰巧重合」（从前说"不是子集 / 不封闭"或"不是子群"，都对不上真相） |

**第二同构在 F₂₁ 上的正确姿势**（实测）：`F = F_21`、`K = 闭包(F, a)`、`M = 闭包(F, b)` →
`交(K, M)` = **{e}，且是群对象（C₁）** —— 接着 `商(K, 交(K,M))`、`商(HN, M)` 都能算。
"元素集"那条路现在是**诚实报错**（不再悄悄给一个看着像真的集合）。
顺带回答"元素集怎么继续用"：`∩` / `·` 的结果**确是子群时会自动升级**（定理）；`∪` / `\` 的产物本来就是集合，
要当子群用就 `闭包(…)` 收一下（它的「可做」里就有）。

### 6.18 第十四批做了什么（2026-09-29）——「结果与选择无关时，别让我选」

用户原话：「这么麻烦，我直接生成C3和C7居然不能做积集，还得弄闭包……个人认为只要拉两个子群箭头就应该能做猜对。」

两条改进（都顺着老纪律："菜单/候选不撒谎" + "唯一性由数学保证，不是猜"）：

| 项 | 落点 |
|---|---|
| **画布上的群进候选** | `OpDef.run(a, ctx?)` 多了一个可选的 `OpContext`（`evalDef` 把**画布上已有的群**整理进去，`opContextOf`）。集合运算找不到共同母群时把画布上的群当候选 —— `交(C_3, C_7)` 在 F₂₁ 旁边**直接算**（{e}），不必再写 `闭包(F, a)` |

| **报错只给"照着做有用"的提示** | 记分加一条：提示只在"另一边已经**原位**站住"时才算有料 —— 否则会给"去 A₄ 里指明 K₃ 的位置"这种**指了也没用**的建议（C₇ 照样塞不进 A₄） |

### 6.19 第十五批做了什么（2026-09-29）—— 商群的商群（第三同构 `(G/N)/(K/N)`）

用户原话：「同构第三定理做不了，不能做商群的商群。」（截图：`G=S4, H=A4, N=V4` → `A=H/N`、`B=G/N`、
`D=G/H`，写 `F=B/A` 报「A 与 B 是两个各自构造的群，元素记号碰巧重合……」）

探针复现出的真机制是**陪集成员记号的写法不一致**：
- `A = H/N`（H = A₄）的陪集成员标成 `(234)`、`(124)`…（**带括号**）；
- `B = G/N`（G = S₄）的**同一批**成员标成 `234`、`124`…（**不带括号**）。

core 给不同母群里的元素起 label 的口径不一样，而陪集只留了 label（没留 id）——
按 label 直接比，同一批陪集就成了两批 → `B/A` 的对齐失败；更糟的是两边陪集的 id
都是 `qcoset-i`（撞号），分诊于是还给了句"元素记号碰巧重合"。

| 项 | 落点 |
|---|---|
| **成员记号先归一** | 新增 `gal/semantic.ts#canonicalMemberLabel`：置换记号化成**唯一写法**——解析成轮换 → 每个从最小元起写、轮换按首元排序（`(234)`/`234` → `(2,3,4)`；`(12)(34)` → `(1,2)(3,4)`）。`(12)(34)` 这种双轮换、`(0,1)` 这种元组不会被误认；非置换记号（`a`、`a^2 b`、`e`）原样保留 |
| **关系层也按语义对齐** | `relations.ts#containment` 的第①关从"按 id"升级为"**按语义键对齐**"：普通元素退化成 id 比对（行为与从前一致），陪集按成员集合比。⇒ 真包含 `A₄/V₄ ≤ S₄/V₄`（**正规、指数 2**）现在判得出来；假的 `S₄/A₄ ≤ S₄/V₄`（id 撞号的产物）消失 |
| **图上那条腰的标签跟着变对** | `derive` 里 `KN ↪ GN` 的标签本来现场判定；判据修好后这组（K ⊴ G、指数 2）从 `↪` 变 `⊴` ✓ |

实测（`N` 用**独立构造**的 V₄）：`A=H/N`、`B=G/N` 各自自动翻译 → **`F = B/A` = C₂**、`D = G/H` = C₂
（第三同构两边对上）；关系面板照出 `A ≤ B（正规、指数 2）` 与 `F = B/A（商）`。
