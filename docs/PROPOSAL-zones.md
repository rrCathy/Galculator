## 0. 一句话

**把「一种表达形状」拆成「三种投影」**——对象表仍然只有一份，
`画布 / 工作台 / 草稿区` 是它的三条 `derive`，各有判据、各有产物形状。

现在的界面只有**一个投影**：45 条 op 全部编译成"一行 `H = closure(G, r)`"，
再由 `build.ts`（纯函数）派生成画布节点 / 边 / 面板。
这个设计很干净，但代价是**只有一种表达形状**——
而用户点名的那些东西（集合加结构 → 群、群同态、群作用、半直积、自同构、共轭类）
**天然不是"一行"**。

## 2. 三区是三种投影，不是三份数据

```
                    objects : GalObject[]        ← 唯一的一份
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
   homeOf(v) = 画布    homeOf(v) = 工作台   homeOf(v) = 草稿区
   顶点 / 边            表 / 档案            未成形 / 已弃
```

**为什么不能做成三份数据**：`identity.ts#callKey` 那条缺口⑯就是"同一对象认成两份"
（手打 `I = im(\varphi)` 与点 φ 悬浮球得到两个对象）。
草稿区尤其危险——它天然是"另一堆对象"。⇒ 三区必须共用对象表。

**判据只有一份**：`homeOf(value) → 'canvas' | 'bench' | 'draft'`，
**与 `sortOf` 同构、定义一次三处消费、判不出就回画布**。
（`sortOf` 已经回答"它在图里处于什么位置"，`homeOf` 答的是"它**该被谁**呈现"。）

### 2.1 三区的判据与产物

⚠️ **三区的判据不是同一种**（草稿区那条是用户 2026-10-05 拍板后改的，见 §5）：
**画布 / 工作台问"它是什么"（类型与用途），草稿区问"它此刻是不是暂存的"（状态）。**

| 区 | 判据 | 性质 | 典型对象 | 产物形状 |
|---|---|---|---|---|
| **画布** | 产物是**顶点或边**（`sortOf ∈ {vertex, edge}`）且**要与别的对象一起看** | 类型判据 | `G ↷ Ω` · `ker` · `π` · `≅` · 同构定理的交换图 | 一个节点 / 一条箭头（**现有全部照旧**）|
| **工作台** | 产物是**表或档案**（要逐行读、要能引用） | 用途判据 | 运算表 · 公理档案 · 生成元→像 · 置换表 · 共轭类 · 元素表 | **常驻结构化卡片**（不是一行文本）|
| **草稿区** | **不设准入**（用户原话：「什么对象都能放」）——只问"此刻是不是暂存" | **状态判据** | 试算中的表达式 · 失败尝试 · 暂时用不上的 · 分解与判定 · 画布放不下的大件 | 可回收的一行（**带"扶正"成对象的入口**）|

⚠️ **`list` / `scalar` 不是"该进草稿区"**。`Sub(G)`（子群集）已经有家
（`sortOf = 'list'` ⇒ 信息面板 list 档）——它只是**默认不占草稿位**。
**草稿区与 `sortOf` 正交**（§5.3）：一个 `list` 可以既在信息面板、又被搁在草稿区。

## 3. 工作台：**功能入口为主**，对象详情为辅（2026-10-05 修订）

> ⚠️ 本节原先写的是「槽位＝**对象**」（一列对象列表 + 选中对象的详情）。
> **照那个做出来的东西被用户当场否了**：
> 「什么叫得选对象才能用工作台？那叫什么工作台？我创建了一个集合，
> 这个工作台怎么只能看？工作台难道不就是用来放什么添加群结构之类的功能吗？」
>
> 病根：「槽位＝对象」这句话把**入口**换成了**详情**。用户进工作台是要**做一件事**
> （给这个集合加结构、算两个群之间的同态），不是**看一个东西**。
> 对象只是那件事的参数，工作台不该要求先选中它。
>
> **判据的分工（保留第一版那半）**：对象详情仍然有价值（左上的「信息」抽屉也有），
> 所以它在工作台右栏**继续存在**，但它是**配角**；主栏是**全部 7 类 36 个操作**。

### 3.1 两栏，各司其职（**都不要求先选中对象**）

```
┌─ 工作台（从底部升起，画布当背景）───────────────────────────┐
│ ▼工作台                              [焦点对象 G]           │
├──────────────────┬─────────────────────────────────────────┤
│ **任务栏**        │ **细节区**（焦点是群 / 结构 / 集合时才有）│
│ 结构/映射/作用  3 │  结论区（identity / 阶 / 生成元 / …）   │
│   structure(P,…) │  元素表（逐元素一行）                   │
│   map(G,H,…)     │  共轭类 / 子群表 / 运算表 / 公理档案     │
│   customAction(…)│                                          │
│ 群与分解       9  │  ——焦点是映射 / 作用 / 关系时给一句      │
│   semidirect…    │    「它是边，答案在画布上」              │
│ 子群与正规性   7  │                                          │
│ 作用与轨道     8  │                                          │
│ 映射的核与像   2  │                                          │
│ 集合运算       5  │                                          │
│ 关系           2  │                                          │
└──────────────────┴─────────────────────────────────────────┘
```

| | 任务栏（左）| 细节区（右）|
|---|---|---|
| **是什么** | **全部能力清单**（`gal/workbench.ts` 一处定义）| 焦点对象的结构细节（复用 `SectionBody`）|
| **需要选中对象吗** | **不需要** —— 空画布上点一条就进槽位 | 需要（没选就显示一句，不影响左边）|
| **点一下会发生什么** | 有焦点就**带上它当第一参数**（`canPick` 判位收不收），没焦点就 `picked: []` 进 pending | 只展开一节（可逐节收起）|

### 3.1b ⚠️ 参数必须**在工作台里凑齐**：对象槽位（2026-10-05 自查补）

**这是 P1-2 上线后自查抓到的结构性卡死。** 工作台里点一条二元操作（如
`semidirectProduct(N, H)`）⇒ pending 提示"去画布点 N" ⇒ **而工作台升起时
`top≈380`、画布节点自动布局在 `y≈450` ⇒ 节点全被盖住** ⇒ 点不动、pending 永远挂着。
真机截图里 pending 条让用户"去画布点对象"，**而画布上一个节点都看不见**。

⇒ 工作台的细节区在 `pending` 时切成**槽位区**：

```
正在选对象：semidirectProduct(N, H)   （在下面点，不用去画布）
[1] N  = A_4
[2]    待选：H（群）
点一下填进第 2 位：[H  C_2]
```

- 判据用 `canPick` —— **与"画布上点节点"同一个函数**，所以工作台列出的候选
  与画布上高亮的可点节点完全一致（不会"这里说能选、点下去报错"）。
- 点击直接复用 `App.tsx#onNodeClick`：**点槽位候选与点画布节点在语义上是同一件事**
  （"用这个对象"），各写一份必然分家。
- `hasContent` 要**把 pending 算进去** —— 用户很可能在空画布上先点操作、再选对象
  （这正是工作台该支持的方向）。

### 3.2 为什么按族分（而不是按对象分槽，也不是 36 个平铺）

- **按对象分槽**：见上面的病根 —— 那是详情页，不是工作台。
- **36 个平铺**：抬眼看见的是 36 个记不住的英文函数名，**没找到"我要加个结构"在哪**。
- **按族分（7 族，默认全折）**：抬眼看见的是**「加结构 · 群与分解 · 子群与正规性 ·
  作用与轨道 · 映射的核与像 · 集合运算 · 关系」** —— 用户是照"我要做什么"找的，
  不是照记号找的。族头带条数（`9` / `7` / `8` …），哪一族最重一眼可见。

**族的划分依据**：**用户要做什么**，不是 `OpDef.mechanism`（那是内核怎么算的分类）。
族内按钮上写**纯 ASCII 函数式记号**（`semidirectProduct(N, H)`，照抄就能敲），
角标写这条要几个对象（`benchArity`，与 `objectArity` 同源 —— 标"1 个对象"却要人点两个
比不标更坏）。要弹编辑器的那三条画一道左边（`structure` / `map` / `customAction`）。

**覆盖纪律**：`gal/workbench.ts` 模块加载时 `assertPartition()` 断言
「分组 ∪ 排除 ＝ 全部 45 条」且**互不重叠** —— 加了新 op 却没归类 ⇒ **加载即抛**，
不会"悄悄出现在没人看得见的地方"。**排除的 11 条各自带理由写在表里**：

| 排除 | 理由 |
|---|---|
| `pointSet` / `labeledSet` / `smallGroup` | 凭空造（实参全是标量），归「目录」 |
| **`contains` / `isomorphism`** | **用户 2026-10-05 拍板**：这两个是"两个对象之间的关系"（产出 `relation`，画布上落成一条可点的边），按本节分区定义属**画布**。入口仍在 ⊕ 球菜单（`multiOps` 里含这两个）与拖拽连线 |
| 6 条纯整数算术 | U47"计算先不弄" |

### 3.3 三个已有编辑器（`MapBuilder` / `ActionBuilder` / `StructureBuilder`）

形态高度同构：源 + 参数 + 逐项填 + **产出一行定义**。它们是**同一个组件的三个配置**，
P0-2 已把它们收成 `ui/CardEditor.tsx`（净减 35 行）。

⚠️ 它们是**贴底居中的浮层**，工作台也贴底 ⇒ **必须显式让位**：
开着编辑器时细节区收成一句提示（`.bench-detail.busy`），**任务栏留着**——
用户改主意要点别的操作时不必先关编辑器。

### 3.3 输入输出的重新设计（用户明确点了这块）

| 现在 | 问题 | 工作台里 |
|---|---|---|
| 弹窗式编辑器盖住画布 | 填一半被误触（`App.tsx` 有特判）| 常驻卡片，不盖画布 |
| 表提交后消失 | 只能点开第三层面板再看 | 表就在那儿，可引用 |
| 报错语与结果分居两块 | 填错时不知道哪一行错了 | 逐行内联报错（`MapBuilder` 已有 `violation` 的定向提示，搬到行上）|
| 结论是一行字 | 引用不了 | 结论块 + 「照抄这一步」（`OpDef.notation` 已经是函数式，见 U54）|

## 4. 布局：**从边缘升起的面板**，画布始终是背景

**用户 2026-10-05 定案**（原话：「工作台应该是从底部弹出的框，并且能在底部收起，交换图画布充当背景。
草稿我想从右侧弹出，在右侧收起」）：

| 区 | 方向 | 收起的形态 | 画布 |
|---|---|---|---|
| **工作台** | 从**底部**升起 | 贴底一条胶囊（点它落回去）| **背景**（不被挤压、不换布局）|
| **草稿区** | 从**右侧**滑出 | 贴右一条胶囊 | 同上 |

现有 v3 决策（`INTERACTION.md` §5）已定死"**画布不给抽屉让位**"。
所以两区都是**浮在画布上**的（`position: absolute`），**不占布局**——
`CanvasView` 的尺寸计算与格点布局**一行都不改**，面板升起时画布**不重排**。
这与"三栏并排"是**根本不同**的事：后者把宽度切掉，前者只是盖住一小块。

### 4.1 为什么工作台在底部而不是右侧

- **它要放表**（运算表 n×n、元素表 n 行）—— 那东西**宽而矮**，横向铺开最省地方；
  右侧是竖条（298px 那类），塞一张 4×4 的表就得横滚。
- 底部那条**输入球**已经在那里了（P0-1 的编辑器卡片也在那里）⇒ 底部本来就是"输入区"，
  工作台放这儿是**同一族东西堆在一起**，不是新开一处。
- 右侧留给草稿区：草稿是**一列行**（每条一行，可扫描），竖条天生合适。

### 4.2 两区同时开着怎么办

**允许同时开**（工作台在底、草稿在右，互不遮挡），但各占一块：
底部 ≤ 视口高 **45%**、右侧 ≤ 视口宽 **320px**。
**窄窗（≤1080px）**：草稿区自动收（它是"备查"，工作台是"正在看"）。

## 5. 草稿区：**什么都能放**（用户 2026-10-05 拍板）

> 用户原话：「**草稿区就是草稿区，什么对象都能放。**」

这一句定下的不只是"收什么"，而是**判据的类型**——它与前两区**根本不同**：

| 区 | 判据问的是 | 性质 |
|---|---|---|
| 画布 | 这个值**是什么形状**（顶点 / 边）？| **类型判据**（`sortOf`）|
| 工作台 | 这个值**要不要逐行读**（表 / 档案）？| **用途判据** |
| **草稿区** | 这个值**现在是不是"暂存"的**？| **状态判据** |

⇒ **草稿区不是 `homeOf` 的一档，而是对象表上的一个状态位。**
前两区是"它天然属于哪"，草稿区是"用户此刻把它搁在一边"——**一个对象可以在草稿区，
也可以同时在画布上**（`V_4` 既是草稿里的一个想法、也可以是画布上的一个节点）。

### 5.1 这条决定解决了什么

- **`HISTORY` 里"草稿画布（用户构思）"从 U21 挂到现在**：现在输入球一关，
  试算表达式 / 失败的尝试 / 算错了想回头看的，全都丢了。
  `USABILITY` ⑫ 只解决了"定义行别丢"，**试算过程仍然丢**。
- 用户明确不要"分类"：**"什么对象都能放"** ⇒ 不设准入判据、不做自动归类。

### 5.2 代价与必须配套的一条纪律

**什么都能放 ⇒ 它天然会变成垃圾桶。** 这不是设计洁癖，是可预见的结果：
一个不设准入的收纳区，进去之后**就找不回来了**（用户自己说的"草稿"的原义）。

⇒ **唯一的配套纪律**：草稿区里的每一条都必须**能一键扶正成正式对象**
（草稿 = 尚未决定要不要的东西，不是"被淘汰的东西"）。
这一条与"什么都能放"不冲突：**准入不限，出口必须**。

### 5.3 `homeOf` 因此要改签名

原案把三档写成 `homeOf(value) → 'canvas' | 'bench' | 'draft'`，现在**草稿那档不是值决定的**。
改成两条判据（都在同一处定义，别散成两份）：

```ts
/** 这个值**天然**属于哪一区（草稿区不在其中 —— 草稿是状态，不是归属）。 */
homeOf(v: GalValue): 'canvas' | 'bench'
/** 它此刻是不是"暂存在草稿区"的。 */
isDraft(id: ObjectId): boolean
```

⚠️ **别把 `isDraft` 混进 `homeOf`**：`homeOf` 是**纯函数、只看值**（可缓存、可测）；
`isDraft` 依赖**用户操作历史**（可变的）。混在一起会让"草稿"这条状态污染所有投影。

### 5.4 草稿区放什么（举例，不设限）

| 类别 | 例 |
|---|---|
| 未成形的表达式 | `N_G(A, B)`（还没点计算）· 半截 `closure(G, …)` |
| 失败的尝试 | 报错的那一行，**留着回头看**（现在报错就消失）|
| 只是暂时用不上的 | 算完的 `Syl(G, 3)`，这一轮不查它 |
| 分解 / 判定 / 序列 | `S_4 ≅ A_4 ⋊ C_2`（算得出、没有节点形状）—— 也可以扶正进工作台的结论块 |
| 大件 | 30 阶的群、93 个小群那一档 —— 画布放不下的 |

## 9. 下一步做什么（2026-10-05 用户问）

> 用户原话：「草稿区就是草稿区，什么对象都能放。接下来可以做什么？」

**建议：P0 —— 把三个模态编辑器改成常驻卡片，不挪任何区。**

理由（每条都有账）：

| 为什么是 P0 | 证据 |
|---|---|
| **用户感知最大** | 用户点名的三件（集合加结构、群同态、群作用）现在都是**盖住画布的弹窗**；`App.tsx` 还得写特判防误触 |
| **一行区都不用挪** | 三个编辑器本来就在画布上，改成右侧常驻卡是**纯形态变化** ⇒ 走查的 DOM 大多不用改 |
| **它是 P1 的地基** | 工作台的槽位＝对象；三个编辑器形态同构（源 + 参数 + 逐项填 + 产出一行），**该合成同一个卡片组件的三个配置** —— P0 就是那个合成的第一步 |
| **零覆盖的组件要先有覆盖** | `ui/MapBuilder` 是 `USABILITY §7` **唯一标着"⏳ 仍未覆盖"**的面。P0 要动它 ⇒ **先补走查**（P0 的第 0 步）|

**顺序**：

```
P0-0  补 ui/MapBuilder 走查（纯新增，不改代码）
P0-1  三个编辑器 → 右侧常驻卡片（不挪区、不动画布布局）
P0-2  合成一个 CardEditor 组件（三个配置），删掉三份重复的表单骨架
P1    homeOf 判据 + 工作台（对象槽位 + 表/档案常驻）
P2    草稿区（状态位 isDraft + "扶正"入口）
P3    画布做减法（细节全交出去，自己专心交换图）
```

⚠️ **P0/P1 会动 `InfoDock` 与 `CanvasView` 的 DOM** ⇒ 走查（34 套 1222 条）要跟着改。
**这正是"先清账"的回报**：判据底座干净了（`paramAccepts` 收得到 op 上下文），
改布局时不必再分心查"这个候选是不是真的撒谎"。
